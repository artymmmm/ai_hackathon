# CLAUDE.md

Хакатон ДКБ, 2 этап. Три кейса по кибербезопасности решаются одним ядром и тремя плагинами.

- **`STATE.md` — текущее состояние работ. Читать первым при старте новой сессии.**
- `PLAN.md` — техническая стратегия и архитектура.
- `report/journal.md` — журнал действий, из него нарезаются отчёты по кейсам.
- Этот файл — правила работы в репозитории.

## Часть I. Проектные факты (не переоткрывать заново)

### Окружение

- Питон только из `.venv` (CPython 3.12): `.venv/bin/python`. Системный `python3` — 3.14 без pandas,
  а `pandas` под 3.9 не умеет parquet. Не чинить это, просто пользоваться venv.
- Установлено: pandas, pyarrow, openpyxl, scikit-learn, anthropic, tqdm, pydantic.
- Ставить пакеты через `uv pip install`, не через `pip`.

### Датасеты

| Кейс | Путь | Объём | Схема |
|---|---|---|---|
| 1 | `case 1/data/*.parquet` | 100 000 train + 100 000 test | `uid, domain, document_type, document_description, document_format, locale, text, spans, text_tagged` |
| 2 | `case 2/prompt-injection-safety/data/*.parquet` | 50 000 train + 10 000 test | `text, label` |
| 3 | `case 3/3 кейс_датасет.csv` | 18 864 фрагмента | `unique_id, code` |

**Кейс 1:** `spans = [{start, end, label}]` — точный span-level ground truth, 55+ типов PII/PHI.
README датасета врёт про 50k, реально по 100k в каждом сплите.

**Кейс 2 — три класса, а задание требует два:**

| label | смысл | маппинг в задание |
|---|---|---|
| 0 | безопасный запрос | `safe` |
| 1 | замаскированная инъекция (обёртки в код, ролевые игры, обфускация) | `injection and malicious` |
| 2 | прямой вредоносный запрос без маскировки | `injection and malicious` |

Распределение train: 23414 / 22586 / 4000. Test: 4557 / 4443 / 1000.
Класс 2 сильно меньше — учитывать при стратификации и при подсчёте метрик.
Внутреннее различие 1 vs 2 сохранять как под-тип: задание прямо описывает обе разновидности,
и умение их разделять — бонус, а не шум.

**Кейс 3:** это **C/C++** (ядро Linux, SMB-драйвер, Blink), а не Python. Лейблов нет вообще.
Приложенный HF-датасет `python_vulnerability_remediation` — Python и другого происхождения,
годится только как источник few-shot примеров и формулировок CWE.
Медиана фрагмента 393 символа, p90 — 1849, максимум — 240 969: длинные резать по функциям,
не обрезать молча.

### Жёсткие запреты

- **Никогда не исполнять и не компилировать код из датасета кейса 3** — ни фрагменты, ни
  собственные предложенные исправления. Это прямое требование задания. Анализ только статический.
- Не коммитить датасеты, `.venv`, ключи и токены.
- Не отправлять данные кейсов никуда, кроме выбранного LLM-провайдера.

## Часть II. Провайдер LLM

**Прогон пойдёт, скорее всего, через OpenRouter, а не напрямую через Anthropic.**
Поэтому весь код обязан быть провайдер-агностичным.

- Единственная точка контакта с LLM — `core/llm.py`. Никакой другой модуль не импортирует
  ни `anthropic`, ни `openai`.
- Базовый транспорт — **OpenAI-совместимый** (`/v1/chat/completions`): его понимают OpenRouter,
  локальные раннеры и большинство прокси. Anthropic SDK — опциональный второй бэкенд за тем же
  интерфейсом.
- Модель задаётся строкой из конфига (`anthropic/claude-opus-4.5`, `openai/gpt-4.1`, что угодно),
  а не хардкодится в коде кейса.
- Не использовать провайдер-специфичные фичи как обязательные. Prompt caching, Batch API,
  extended thinking — только как опциональная оптимизация с обязательным fallback на обычный вызов.
- Структурированный вывод: не полагаться на нативный structured output. Просить JSON в промпте
  + строгий парсинг + повтор при провале. Это работает везде.
- Ключей в окружении сейчас нет (`ANTHROPIC_API_KEY` не задан, `ant` не установлен).
  Не пытаться делать живые вызовы без явной команды. Всё, что можно проверить без сети —
  проверять без сети.

### Обязательные свойства `core/llm.py`

- Кеш ответов в SQLite по хешу `(промпт, модель, параметры)` — пересчёт метрик должен быть
  бесплатным и мгновенным.
- Режим `--dry-run`: пайплайн проходит целиком на заглушках, без единого сетевого вызова.
- Учёт токенов и стоимости по каждому прогону — цифры идут в отчёт.
- Ретраи с экспоненциальной задержкой, ограничение параллелизма, аккуратная обработка 429.

## Часть III. Правила кода

### 1. Думать до кода

Не додумывать. Не прятать непонимание. Проговаривать компромиссы.

- Явно называть свои допущения. Не уверен — спросить.
- Если возможны несколько трактовок — показать их, а не выбрать молча.
- Если есть решение проще — сказать об этом. Возражать, когда есть основания.
- Непонятно — остановиться, назвать что именно непонятно, спросить.

### 2. Сначала простота

Минимум кода, решающий задачу. Ничего впрок.

- Никаких фич сверх запрошенного.
- Никаких абстракций ради одного места использования.
- Никакой «гибкости», которую не просили.
- Никакой обработки невозможных сценариев.
- Написал 200 строк там, где хватило бы 50 — переписать.

Исключение, зафиксированное осознанно: `core/` **должен** быть переиспользуемым между тремя
кейсами. Это требование продукта, а не спекулятивная абстракция.

### 3. Хирургические правки

Трогать только необходимое. Убирать только за собой.

- Не «улучшать» соседний код, комментарии и форматирование.
- Не рефакторить то, что не сломано.
- Держаться существующего стиля, даже если сам сделал бы иначе.
- Заметил постороннюю мёртвую строку — сказать, а не удалять.
- Удалять импорты и переменные, осиротевшие **из-за твоих же** изменений.

Проверка: каждая изменённая строка прослеживается до запроса пользователя.

### 4. Исполнение через проверяемую цель

Задачу превращать в критерий успеха и крутить цикл до его выполнения.

- «Добавь валидацию» → «написать тесты на невалидный ввод, довести до зелёного».
- «Почини баг» → «написать тест, воспроизводящий баг, довести до зелёного».
- Для многошаговых задач — короткий план вида «шаг → чем проверяю».

Для этого проекта основной критерий успеха — **метрика на размеченной выборке**, а не
«выглядит правдоподобно». Кейсы 1 и 2 имеют ground truth: любое утверждение о качестве
подкрепляется числом.

### 5. Границы владения файлами

Над проектом работают несколько агентов параллельно. Каждый пишет только в свою зону:

| Зона | Содержимое |
|---|---|
| `core/` | ядро, общее для всех кейсов |
| `cases/pii/` | кейс 1 |
| `cases/guard/` | кейс 2 |
| `cases/codereview/` | кейс 3 |
| `research/` | разведка, матчинг датасетов, разовые заметки |
| `out/` | артефакты прогонов: xlsx, json, метрики |
| `report/` | **только координатор.** Журнал работы и итоговые отчёты. Агенты сюда не пишут |

Итоговое описание своей работы агент кладёт в `cases/<зона>/findings.md`, **не** в `report.md`:
инструмент записи блокирует имена файлов, содержащие `report`, как защиту от агентских
самоотчётов. Если такой файл всё же нужен — писать через Bash heredoc.

Нужен файл из чужой зоны — не править, а сказать об этом. Общий контракт `Verdict` в
`core/schema.py` менять нельзя в одностороннем порядке.

### 6. Git

- Репозиторий пока не инициализирован. Если инициализируется — коммитить после каждой
  законченной задачи, conventional commits (`feat:`, `fix:`, `refactor:`, `chore:`).
- Перед коммитом посмотреть `git diff` и описать в сообщении, что реально изменилось.
- Датасеты, `.venv`, ключи — в `.gitignore`, не в индекс.
