# ДКБ, 2 этап — три кейса по кибербезопасности на одном ядре

Три задания решены одним конвейером и тремя плагинами: обезличивание ПДн (кейс 1), защита
от prompt-инъекций (кейс 2), поиск уязвимостей в коде (кейс 3). Общее ядро — загрузка данных,
провайдер-агностичный клиент LLM с кешем, единый контракт вердикта, экспорт в xlsx/json.

| Кейс | Задача | Итог | Объём замера |
|---|---|---|---|
| 1 | обезличивание PII/PHI | **F1 0.919** (гибрид детекторы + LLM) | 200 документов, эталонные span'ы |
| 2 | детект инъекций и вредоносных запросов | **F1 0.989**, FPR 1.54% | 1000 документов теста |
| 3 | поиск уязвимостей в C/C++ | **F1 0.386**, FPR 0.128 | 600 фрагментов, восстановленная разметка |

Числа живые: получены реальными вызовами LLM, сырые вердикты каждого прогона лежат
в `out/bench/`. Разбор, почему они такие, — в `report/journal.md`.

## Быстрый старт

```bash
# окружение (CPython 3.12)
uv venv && uv pip install pandas pyarrow openpyxl scikit-learn tqdm pydantic

# проверка всей цепочки без единого сетевого вызова
.venv/bin/python run.py --case 1 --sample 20 --split test --dry-run

# живой прогон: ключ провайдера в .env (в репозиторий не коммитится)
.venv/bin/python run.py --case 3 --sample 50 \
  --model deepseek-chat --base-url https://api.deepseek.com --api-key-env DEEPSEEK_API_KEY
```

`run.py --case 1|2|3` находит плагин (`cases/pii`, `cases/guard`, `cases/codereview`),
прогоняет `core.pipeline.run_pipeline` и кладёт результат в `out/case{N}_verdicts.{xlsx,json}`.
Модель, провайдер и цены задаются флагами — ничего не захардкожено.

## Что здесь поставка, а что журнал измерений

Репозиторий содержит и решение, и всю историю его проверки. Это разные вещи, и путать их
не надо.

**Поставка — код, который исполняется в проде:**

```
run.py                      единая точка входа
core/llm.py                 OpenAI-совместимый клиент: кеш SQLite, ретраи, учёт токенов, dry-run
core/{data,pipeline,eval,export,schema}.py   загрузка, конвейер, метрики, выгрузка, контракт Verdict
cases/pii/{detectors,aliaser,llm_layer,verify}.py        кейс 1
cases/guard/{features,taxonomy,baseline,model,grey_zone}.py   кейс 2
cases/codereview/{reviewer,reviewer_configs,knowledge,patch_check}.py   кейс 3
kb/                         правила CERT C и карточки CWE для кейса 3
```

**Журнал измерений — всё остальное.** Полсотни скриптов `cases/*/run_*.py`, `*_experiment.py`,
`*_diagnostics.py` — это проверенные гипотезы, а не части решения. Каждый существует потому,
что на него ссылается конкретный замер в отчёте: `run_gpt5mini_cert_only_600.py` — сравнение
моделей, `run_knowledge_ablation_600.py` — абляция блока знаний, `run_oracle_cwe_516.py` —
оракульный тест, доказавший, что подсказка верного CWE не помогает. Отрицательные результаты
оставлены намеренно: они и есть обоснование того, почему поставка выглядит именно так.

## Где числа

| файл | что в нём |
|---|---|
| `out/bench/results.csv` (+`.xlsx`) | одна строка на конфигурацию: P/R/F1/FPR, n, токены, заметка |
| `out/bench/*.json` | сырые вердикты и usage каждого прогона — источник всех метрик |
| `report/model_benchmark.md` | сравнение моделей на фиксированных наборах id |
| `report/journal.md` | что делали, что вышло и почему — из него нарезаны отчёты по кейсам |
| `STATE.md` | текущее состояние, закрытые тупики, известные ловушки |
| `research/case3_recovered_labels_v4.csv` | восстановленная разметка кейса 3 (в исходных данных лейблов нет) |

Метрики пересчитываются по сырым вердиктам бесплатно, без обращения к LLM:

```bash
.venv/bin/python cases/codereview/evaluate.py --verdicts out/bench/case3_cert_only_600.json
```

Сравнение моделей идёт только по фиксированным наборам id (`out/bench/case3_eval600_ids.txt`
и `--ids-file`) — иначе результаты несопоставимы.

## Чего в репозитории нет

- **Датасеты** (`case 1/`, `case 2/`, `case 3/`) — выдаются организатором, весят слишком много.
- **Ключи** (`.env`), CA-бандл GigaChat (`certs/`), веса дообученной модели (589 МБ).
- **`.venv`** и кеши ответов LLM, кроме тех, что нужны для воспроизведения метрик.

Фрагменты кода из датасета кейса 3 присутствуют внутри файлов вердиктов в `out/bench/`:
без них вердикт нечитаем, а метрика непроверяема.

## Два правила, соблюдённых по всему коду

1. **Код из датасета кейса 3 нигде не исполняется и не компилируется** — ни фрагменты,
   ни предложенные исправления. Анализ только статический, это требование задания.
2. **Провайдер-агностичность.** Единственный модуль, знающий про API LLM, — `core/llm.py`.
   Прогоны выполнялись на DeepSeek, OpenRouter (gpt-5-mini, qwen3-30b) и GigaChat одним
   и тем же кодом, различие — строка модели в конфиге.

## Известные ограничения

Названы честно и подробно разобраны в `STATE.md`:

- **Кейс 3 объективно труден.** Фрагменты — реальные CVE из ядра Linux и Chrome, где уязвимость
  почти никогда не видна внутри одной функции. Accuracy показывать нельзя: при доле уязвимых
  5.6% тривиальное «всё безопасно» даёт 94%. F1 тоже вводит в заблуждение — «пометить всё
  уязвимым» даёт 0.454 и бьёт все измеренные модели, поэтому рядом с F1 идут Youden J и MCC.
- **Кейс 3 исчерпан по промптам.** Девять гипотез улучшения проверены и закрыты замером,
  включая RAG-подобный подбор знаний и более дорогую модель. Все — в разделе «Закрытые тупики».
- **Кейс 2: F1 0.989 подозрительно высок** — датасет шаблонный, часть сигнала приходится
  на стилистику генератора.
- **Разметка кейса 3 восстановлена, а не выдана.** Метод сопоставления и его проверки —
  в `research/case3_label_matching*.md`.
