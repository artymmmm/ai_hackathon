# Хакатон ДКБ, второй этап

Три задания по кибербезопасности решены одним конвейером и тремя подключаемыми кейсами:
обезличивание документов, защита от инъекций в промпт, ревизия кода. Общая часть — загрузка
данных, вызов языковой модели, единый формат вердикта и выгрузка в xlsx и json. Кейс добавляет
к этому только свою логику.

Отчёты: `report/case1.md`, `report/case2.md`, `report/case3.md`. Ход работы целиком, со всеми
промежуточными замерами и опровергнутыми гипотезами, — `report/journal.md`.

## Результат работы

| Кейс | Решение | Качество | Выборка |
|---|---|---|---|
| №1, обезличивание | детекторы плюс языковая модель | precision 0.951, recall 0.889, F1 0.919 | 200 документов |
| №2, защита от инъекций | офлайн-классификатор плюс языковая модель в серой зоне | precision 0.987, recall 0.991, F1 0.989, доля ложных срабатываний 1.54% | 1000 документов |
| №3, ревизия кода | один вызов модели на фрагмент | precision 0.540, recall 0.300, F1 0.386, доля ложных срабатываний 0.128 | 600 фрагментов |

Числа получены реальными прогонами, не оценкой. Сырые вердикты каждого прогона лежат
в `out/bench`, метрики пересчитываются по ним заново без обращения к сети.

## Как запустить

Питон 3.12 из виртуального окружения, зависимости — pandas, pyarrow, openpyxl, scikit-learn,
tqdm, pydantic.

Проверка всей цепочки на заглушках, без единого сетевого вызова:

```
.venv/bin/python run.py --case 1 --sample 20 --split test --dry-run
```

Живой прогон:

```
.venv/bin/python run.py --case 3 --sample 50 \
  --model deepseek-chat --base-url https://api.deepseek.com --api-key-env DEEPSEEK_API_KEY
```

Ключ читается из файла `.env` по имени переменной, указанной в `--api-key-env`. Модель, адрес
провайдера и цены токенов задаются флагами: протокол обмена OpenAI-совместимый, поэтому решение
работает с любым провайдером, поддерживающим этот интерфейс. За время работы оно прогонялось на
девяти моделях четырёх провайдеров без правок кода кейсов.

Результат каждого прогона выгружается в `out/case{N}_verdicts.xlsx` и `.json`.

## Что здесь решение, а что журнал измерений

Репозиторий содержит и то и другое, и это разные вещи.

Решение — код, который исполняется в рабочем прогоне:

```
run.py                          выбор кейса, прогон, выгрузка
core/llm.py                     вызов модели: кеш ответов, повторы, учёт токенов, режим заглушек
core/data.py                    загрузка трёх датасетов
core/pipeline.py                конвейер, общий для кейсов
core/schema.py                  формат вердикта
core/eval.py, core/export.py    метрики и выгрузка
cases/pii/                      кейс №1: detectors, aliaser, llm_layer, verify
cases/guard/                    кейс №2: features, taxonomy, baseline, model, grey_zone
cases/codereview/               кейс №3: reviewer, reviewer_configs, knowledge, patch_check
kb/                             правила CERT C и карточки CWE для кейса №3
```

Всё остальное в `cases/*` — скрипты вида `run_*.py`, `*_experiment.py`, `*_diagnostics.py` —
это проверенные гипотезы. Каждый существует потому, что на него ссылается конкретное число
в отчёте: `run_knowledge_ablation_600.py` — проверка того, влияет ли содержание блока знаний,
`run_gpt5mini_cert_only_600.py` — сравнение с более дорогой моделью, `run_oracle_cwe_516.py` —
проверка того, помогает ли модели подсказка верного типа слабости. Ни один из них не участвует
в рабочем прогоне.

Отрицательные результаты оставлены намеренно. В кейсе №3 их девять, и они объясняют, почему
поставленное решение выглядит просто: сложные надстройки проверены и ничего не дали.

## Где числа

`out/bench/results.csv` — по строке на конфигурацию: precision, recall, F1, доля ложных
срабатываний, размер выборки, израсходованные токены, замечание. Рядом та же таблица в xlsx.

`out/bench/*.json` — сырые вердикты и расход токенов каждого прогона. Из них считается всё
остальное:

```
.venv/bin/python cases/codereview/evaluate.py --verdicts out/bench/case3_cert_only_600.json
```

Модели сравниваются только на фиксированных наборах идентификаторов
(`out/bench/case3_eval600_ids.txt`, флаг `--ids-file`) — иначе результаты несопоставимы.

`research/case3_recovered_labels_v4.csv` — восстановленная разметка третьего кейса: в исходных
данных её нет, и как она получена, описано в `research/case3_label_matching_v3.md`.

## Чего в репозитории нет

Датасеты выдаются организатором и лежат в каталогах `case 1`, `case 2`, `case 3` рядом с кодом.
Ключи провайдеров, сертификаты для GigaChat и веса дообученной модели тоже не хранятся здесь.

Код из датасета третьего кейса нигде не исполняется и не компилируется — ни исходные фрагменты,
ни предложенные исправления. Анализ только статический, это требование задания.

## Ограничения

Разметка третьего кейса восстановлена сопоставлением с внешним источником, а не выдана
организаторами. Эталонный набор содержит 33% уязвимых фрагментов против 5.59% в полном корпусе,
поэтому F1 0.386 нельзя переносить на промышленное распределение без пересчёта. На этом же
наборе тривиальное «пометить всё уязвимым» даёт F1 0.454, так что F1 в третьем кейсе читается
только рядом с показателями Youden J и MCC.

Высокое качество во втором кейсе частично объясняется тем, что датасет шаблонный: часть сигнала
приходится на стилистику генератора, а не на смысл запроса.

Полные списки ограничений по каждому кейсу — в соответствующих отчётах.

## Как велась работа

Задание разрешает использовать агентные системы. Решение построено командой: человек ставил
задачи и принимал результаты, модель Opus в роли координатора проектировала систему и раздавала
работу, агенты Sonnet параллельно писали ядро и три кейса в непересекающихся зонах файлов.

Правило, которого держались: любое утверждение о качестве подкреплено числом, посчитанным
скриптом, а результаты агентов перепроверялись по файлам, а не по пересказу.
