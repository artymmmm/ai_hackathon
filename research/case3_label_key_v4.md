# Кейс 3 — v4 разметка по найденному ключу LineVul

## Откуда ключ

Датасет `realvul/LineVul_Test_Dataset` на Hugging Face содержит колонку `target` (0/1) и,
судя по всему, является самим датасетом кейса 3 с добавленной меткой. Карточка датасета на HF
**не документирует происхождение** — прямого подтверждения «это тот же датасет» от авторов нет.
Тождество установлено только сопоставлением содержимого:

- **Совпадение множества id**: `unique_id` в ключевом parquet (18 864 значения, без дублей)
  совпадает как множество с `unique_id` кейса 3 (18 864 значения, без дублей) — 1:1.
- **Побайтовое совпадение кода**: колонка `code` идентична по каждому `unique_id` между ключом
  и датасетом кейса 3 (проверено по всем 18 864 строкам).
- **Дубликат train/test**: в репозитории `realvul/LineVul_Test_Dataset` лежат два parquet-файла
  (train и test), которые оказались полными дублями друг друга — те же id, тот же код, те же
  метки. Это указывает на неаккуратную публикацию (кто-то продублировал полный сплит), а не на
  честный train/test split, что дополнительно снижает доверие к карточке датасета как к
  источнику метаданных — но не влияет на тождество текста и id, которое проверено напрямую.

Файл ключа (только для чтения, в этом прогоне не публикуется в репозиторий):
`/private/tmp/claude-501/-Users-artemmartynov-claude-ai-hackathon/717ab4fa-30bc-488b-bc75-2b5c1e3ccf8e/scratchpad/linevul_realvul/data/test-00000-of-00001.parquet`
Схема: `unique_id, target, code, __index_level_0__`.

**Оговорка**: то, что колонка называется `target` в датасете с именем `LineVul_Test_Dataset`,
не доказывает, что она размечена тем же процессом/версией CWE-таксономии, что использовалась в
задании хакатона — только то, что это метка "vulnerable/secure" для тех же самых фрагментов кода.
Дальнейшая работа трактует её как ground truth, потому что это единственный найденный источник
прямой (не восстановленной матчингом) разметки для всех 18 864 строк без исключения.

## Что изменилось: v3 → v4

`research/case3_recovered_labels_v3.csv` — разметка, восстановленная матчингом по корпусам
BigVul / DiverseVul / PrimeVul / CVEfixes (см. `research/case3_label_matching.md`).
`research/case3_recovered_labels_v4.csv` — та же схема (`unique_id, recovered_label,
match_source, cwe_id, source_project`), но `recovered_label` = `target` из ключа для всех
18 864 строк, `match_source = "linevul_key"` везде. Колонки `cwe_id` и `source_project`
перенесены из v3 без изменений (ключ их не содержит, а на сам факт vulnerable/secure они не
влияют).

Построено скриптом `research/build_case3_labels_v4.py`, проверки записаны в
`research/case3_labels_v4_checks.json`.

- **101 из 18 864** строк (0.54%) получили другую метку в v4, чем была в v3.
- Разбивка расхождений по исходному `match_source` в v3:

Ожидаемо хуже всего держится `diversevul_only` (79/933 = 8.5% расхождений с ключом) — самый
слабый по надёжности источник матчинга в v3. Даже `both_agree` (два независимых корпуса
согласились) разошёлся с ключом в 6 случаях из 6728 (0.09%) — редкий, но ненулевой шум.

- **В эталонных 150** расхождений 4: `unique_id` = 71857, 66318, 29969, 53312 — все они
  меняют направление метрик на конкретных вердиктах ниже.

## Как сдвинулись метрики

Пересчитано скриптом `research/compute_case3_relabel_metrics.py` по всем 49 файлам
`out/bench/case3_*.json`, которые являются списком вердиктов (150 штук в каждом — полный
эталонный набор). 3 файла пропущены как agg/summary, не список вердиктов (без вердиктов
считать нечего): `case3_critic_usage.json`, `case3_critic_vote_diversity.json`,
`case3_ensemble_gigachat_deepseek_summary.json`. `case3_nemotron-ultra.json` не существовал на
момент прогона (фоновая задача ещё не завершилась) и явно исключён из скрипта по имени файла —
трогать его было запрещено.

Полная таблица — `out/bench/case3_relabel_v4_metrics.csv` / `.json`
(колонки: `file, n, p_v3, r_v3, f1_v3, fpr_v3, p_v4, r_v4, f1_v4, fpr_v4, delta_f1`).

Средний сдвиг F1 по всем 49 конфигурациям: `delta_f1` от −0.0234 до +0.0269, среднее +0.0119,
медиана +0.0143 — v4 в среднем чуть выгоднее для тех же вердиктов, потому что на 4 из 150
эталонных фрагментов метка сменилась с vulnerable→secure или наоборот именно в сторону, где
модели чаще угадывали "новую" метку.
