# GigaChat API — разведка для подключения третьим бэкендом

## Вердикт

**Подключить стоит, но не как замену DeepSeek/OpenRouter, а как опциональный третий
бэкенд для отчёта.** Аргумент для банковского кейса сильный: данные не покидают РФ,
провайдер — Сбер, есть бесплатный freemium-лимит, которого более чем достаточно для
прогона всех трёх кейсов на сколь угодно большой выборке. Код (`core/llm_gigachat.py`)
написан и зарегистрирован как `backend="gigachat"`, но **живых вызовов не делал — ключей
нет**. Всё, что можно проверить без сети, проверено (`--dry-run` не сломан).

Главные риски, которые нужно знать *до* похода за ключом:
1. **TLS-сертификат НУЦ Минцифры** — без него первый же запрос (даже за токеном)
   падает с `SSL: CERTIFICATE_VERIFY_FAILED`. Нужно либо поставить сертификат в систему,
   либо явно передать `cafile=`, либо (не рекомендуется) отключить проверку.
2. **Access token живёт всего 30 минут** и это отдельный OAuth-обмен, а не просто
   API-ключ в заголовке — на каждый первый вызов после протухания токена уйдёт лишний
   round-trip.
3. **Модельный ряд первого поколения (`GigaChat`, `GigaChat-Pro`, `GigaChat-Max`)
   объявлен deprecated** — актуальны `GigaChat-2`, `GigaChat-2-Pro`, `GigaChat-2-Max`.

## 1. Доступ к API

Регистрация — через личный кабинет **GigaChat Studio** (developers.sber.ru), не через
отдельный "API-портал". Шаги:

1. Завести аккаунт в Studio (для физлица — обычная регистрация, паспортные данные/
   верификация личности документация не требует; для ИП/юрлица — отдельная процедура
   с реквизитами организации).
2. Создать проект **GigaChat API** → раздел «Настройки API» → «Получить ключ».
3. В разделе «Авторизационные данные» проекта — `Client ID` и `Client Secret`.
   Ключ (Client Secret) и итоговый Authorization key показываются **один раз** и
   нигде больше не хранятся — если потерян, генерировать заново.
4. **Authorization key** = `base64(Client ID:Client Secret)` — либо Studio выдаёт его
   в готовом виде, либо собрать самому. Именно эта строка идёт в заголовок
   `Authorization: Basic <authorization_key>` при обмене на access token.

Физлицам API **доступен без верификации юрлица** — это отдельная (более простая) ветка
регистрации по сравнению с ИП/организациями. Источники называют её "freemium"-доступом.

## 2. Схема аутентификации (OAuth, обмен ключа на токен)

GigaChat не принимает Authorization key напрямую в запросах к модели — сначала его
нужно обменять на **access token**, который живёт **30 минут**, и обновлять по истечении.

**Endpoint:**
```
POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth
```

**Заголовки (все обязательны):**
```
Content-Type: application/x-www-form-urlencoded
Accept: application/json
RqUID: <uuid4>                      # свежий UUID4 на каждый запрос токена
Authorization: Basic <authorization_key>
```

**Тело:**
```
scope=GIGACHAT_API_PERS             # физлицо; для юрлиц — GIGACHAT_API_B2B / GIGACHAT_API_CORP
```

**Ответ:** JSON с `access_token` и `expires_at` (unix-время истечения, до него — 30 минут
от выдачи). Дальше `access_token` идёт в `Authorization: Bearer <access_token>` на
запросах к `/chat/completions`.

**Практика обновления:** обменивать заранее, не дожидаясь 401 — держать в памяти
`(токен, время_истечения)` и брать новый при подходе к границе (например, за 60 секунд
до `expires_at`), а не по факту ошибки. Лимит на сам эндпоинт токена — до 10 запросов/сек,
так что частое обновление не проблема, но кешировать всё равно нужно: получать новый
токен на каждый вызов модели — лишняя сетевая задержка и ненужная нагрузка на OAuth-сервер.

## 3. TLS и сертификат НУЦ Минцифры

GigaChat API — и `ngw.devices.sberbank.ru` (OAuth), и `gigachat.devices.sberbank.ru`
(модель) — обслуживаются сертификатом, выпущенным российским **Национальным
удостоверяющим центром Минцифры**, которого нет в стандартных системных/питоновских
хранилищах доверенных корневых сертификатов. Без явных мер — `SSL: CERTIFICATE_VERIFY_FAILED:
self-signed certificate in certificate chain` на первом же запросе.

Два варианта решения:

**А. Установить корневой сертификат (рекомендуемый способ).**
Официальный сертификат:
`https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`
Можно либо добавить его в системное хранилище ОС, либо (проще для Python) дописать в
файл доверенных сертификатов `certifi`:
```bash
curl -k "https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt" -w "\n" >> $(.venv/bin/python -m certifi)
```
Подводный камень: это модифицирует файл внутри виртуального окружения — при
пересоздании `.venv` сертификат придётся добавлять заново. Альтернатива без побочных
эффектов на venv — передавать `cafile=<путь_к_сертификату>` явно при создании
`ssl.SSLContext`, не трогая системный/venv-бандл.

**Б. Отключить проверку сертификата (`verify_ssl_certs=False` в официальном SDK,
у нас — неверифицированный `ssl`-контекст).** Работает, но осознанно снижает
безопасность TLS-соединения (уязвимо к MITM). Официальная документация Сбера
такой режим не рекомендует. Приемлемо только для разовых экспериментов, не для
прод-контура банка — иронично для кейса, где мы сами продаём аргумент «данные не
покидают периметр».

`core/llm_gigachat.py` поддерживает оба варианта через переменные окружения (см. §7),
по умолчанию — обычная проверка сертификата средствами `ssl.create_default_context()`
(сработает, только если сертификат уже установлен в системе/venv способом А).

## 4. Тарифы

Официальная страница: `developers.sber.ru/docs/ru/gigachat/tariffs/individual-tariffs`.

**Freemium для физлиц:** суммарный лимит **365 млн токенов в год**, обновляется раз
в 12 месяцев, распределён по моделям неравномерно:

| Модель | Бесплатный лимит/год |
|---|---|
| GigaChat-2 Lite | 250 млн токенов |
| GigaChat-2 Pro | 40 млн токенов |
| GigaChat-2 Max | 25 млн токенов |
| GigaChat-2 Ultra | 50 млн токенов |

(Встречались более старые/противоречивые цифры на сторонних агрегаторах — например
"1 млн токенов" — это устаревшие данные до пересмотра тарифов; ориентироваться на
официальную страницу тарифов Сбера, не на статьи 2024–2025 гг.)

Генерация в freemium-режиме идёт **в один поток** (без параллелизма) — при интеграции
с `complete_many`/`max_concurrency` в `core/llm.py` для GigaChat имеет смысл
выставлять `max_concurrency=1`, иначе часть запросов будет упираться в лимит потоков,
а не токенов.

**Платные пакеты** (цены с НДС, действуют 12 месяцев с оплаты; примерно 0.065–0.65 ₽
за 1000 токенов в зависимости от модели):

| Модель | Пакет | Цена | ₽/1000 токенов |
|---|---|---|---|
| GigaChat-2 Lite | 20М / 100М токенов | 1300 ₽ / 6500 ₽ | 0.065 |
| GigaChat-2 Pro | 3М / 15М токенов | 1500 ₽ / 7500 ₽ | 0.50 |
| GigaChat-2 Max | 3М / 15М токенов | 1950 ₽ / 9750 ₽ | 0.65 |
| Embeddings | 50М токенов | 700 ₽ | 0.014 |

Расход считается в **токенах входа+выхода суммарно** (в отличие от многих западных
провайдеров с раздельной ценой input/output — у GigaChat одна цена за токен на
модель). Это отличается от структуры `_PRICING_PER_1M` в `core/llm.py`
(input, output) — при желании точно считать `cost_usd` для GigaChat нужно передавать
одинаковые `price_per_1m_input`/`price_per_1m_output` через флаги `--price-in`/`--price-out`
(в рублях, а не USD — `core/llm.py` не делает конвертацию валют, это на совести
вызывающего).

## 5. Модели

Актуальное (второе) поколение — все с контекстным окном **128 000 токенов**:

| Модель | Профиль | Параметры (оценка) | Заметки |
|---|---|---|---|
| `GigaChat-2` | быстрая, для простых задач | ~8B | самая дешёвая |
| `GigaChat-2-Pro` | баланс качества/скорости | ~70B | следование инструкциям |
| `GigaChat-2-Max` | максимальное качество | — | function calling, vision, до 8К токенов в ответе |

Модели первого поколения (`GigaChat`, `GigaChat-Plus`, `GigaChat-Pro`, `GigaChat-Max`
без суффикса `-2`) объявлены deprecated и по факту редиректят на аналоги второго
поколения — **использовать имена с `-2`**, чтобы не полагаться на неявный редирект.

## 6. Совместимость с OpenAI API

**Частичная**, официально описана как "message format... partially compatible with
OpenAI API". Практические выводы:

- Базовый URL: `https://api.giga.chat/v1` (актуальный, с июля 2026) либо старый
  `https://gigachat.devices.sberbank.ru/api/v1` (продолжает работать для существующих
  интеграций). Путь `/chat/completions` — как у OpenAI.
- **Аутентификация не OpenAI-style.** Вместо статичного `Authorization: Bearer <api_key>`
  нужен предварительный OAuth-обмен (см. §2) — то есть нельзя просто подставить
  GigaChat в существующий `_openai_compat_call` из `core/llm.py`, заголовок
  `Bearer <api_key_env>` там ожидает готовый ключ, а не токен с TTL 30 минут.
  Поэтому у GigaChat — отдельный файл `core/llm_gigachat.py`, а не переиспользование
  `openai_compat` с другим `base_url`.
- **Function calling** поддерживается (аналог tool calling у OpenAI).
- **JSON/structured output**: начиная с GigaChat-версии 30.1 есть `response_format`
  с `type: json_schema` (эмулируется через function calling), но со значимым
  ограничением — схемы с `anyOf`/`oneOf`/`allOf` (а значит и большинство
  Pydantic-моделей с `Union`) не поддерживаются. **Мы это не используем**: проект
  осознанно строит JSON через промпт + `complete_json()` со строгим парсингом и
  повтором при провале (см. `core/llm.py`, докстринг), не полагаясь на нативный
  structured output ни у одного бэкенда — эта проблема GigaChat нас не касается.

## 7. Что нужно от пользователя, пошагово

1. Зарегистрироваться в **GigaChat Studio** (developers.sber.ru), физлицом — без
   верификации юрлица.
2. Создать проект **GigaChat API**, в «Настройках API» получить `Client ID` /
   `Client Secret`, собрать или скопировать готовый **Authorization key**
   (`base64(Client ID:Client Secret)`). Сохранить сразу — второй раз Studio его
   не покажет.
3. Установить сертификат НУЦ Минцифры (см. §3, вариант А) — иначе первый же вызов
   упадёт по TLS ещё до вопроса про ключ.
4. Добавить в `.env` (в том же стиле, что и `DEEPSEEK_API_KEY`):
   ```
   GIGACHAT_AUTH_KEY=<base64 Client ID:Client Secret>
   ```
   Опционально (есть разумные значения по умолчанию в `core/llm_gigachat.py`,
   переопределять не обязательно):
   ```
   GIGACHAT_SCOPE=GIGACHAT_API_PERS        # для юрлица: GIGACHAT_API_B2B / GIGACHAT_API_CORP
   GIGACHAT_BASE_URL=https://gigachat.devices.sberbank.ru/api/v1
   GIGACHAT_TOKEN_URL=https://ngw.devices.sberbank.ru:9443/api/v2/oauth
   GIGACHAT_CA_BUNDLE=/путь/к/russian_trusted_root_ca_pem.crt   # если не ставили сертификат в систему
   GIGACHAT_VERIFY_SSL=false               # НЕ рекомендуется, только для быстрого теста
   ```
5. Прогнать с ключом:
   ```
   .venv/bin/python run.py --case 2 --sample 20 --backend gigachat \
     --api-key-env GIGACHAT_AUTH_KEY --model GigaChat-2-Pro --max-concurrency 1
   ```
   (`--max-concurrency 1` — freemium генерирует в один поток, см. §4).

Если ключа так и не будет — не критично: DeepSeek/OpenRouter уже дают живые метрики
по всем трём кейсам (см. `STATE.md`). GigaChat тут — бонусный аргумент для отчёта
(«решение работает и с российским провайдером, данные не уезжают за рубеж»), а не
блокер сдачи.
