# Кейс 3 — восстановление лейблов, раунд 3: LineVul-порты HF закрывают весь остаток

Продолжение `research/case3_label_matching_v2.md`. Метод хеширования не менялся там, где
применялся (`sha256(re.sub(r'\s+', '', code))`), но решающий источник этого раунда найден не
через приблизительный хеш-матчинг, а через **точное совпадение по `unique_id` и коду
целиком** — см. §1. Файл v2 (`research/case3_recovered_labels_v2.csv`) не тронут, новый —
`research/case3_recovered_labels_v3.csv`. Числа посчитаны скриптом, использованным для сборки
файла; сырой JSON — `research/case3_v3_check_summary.json`.

## TL;DR

- Задача: проверить, дают ли HF-порты LineVul/BigVul хотя бы один новый лейбл для 1270
  фрагментов, которые в v2 остались без пригодного лейбла (`unmatched` 1101 +
  `internal_conflict` 98 + `both_disagree` 71 = 1270).
- Ответ: **да, один источник закрывает все 1270 из 1270**, причём не приблизительным
  хеш-матчингом, а **точным совпадением по `unique_id`**: HF-датасет
  `realvul/LineVul_Test_Dataset` оказался **байт-в-байт копией всего датасета кейса 3**
  (все 18 864 `unique_id`, весь текст `code` совпадает дословно) с добавленной колонкой
  `target` — то есть это готовые лейблы именно к нашему датасету, не к похожему стороннему
  корпусу.
- Согласие с уже размеченными 17 594 фрагментами (BigVul/DiverseVul/PrimeVul/CVEfixes'22
  merge из v2): **99.43%** (17 493 / 17 594), обратное направление поля (флип) даёт **0.57%** —
  однозначно то же направление, инверсии нет, флип не нужен.
- **Эталонные 150 (`out/bench/case3_eval_ids.txt`) не изменились**: v3 использует новый
  источник только для строк с `match_source ∈ {unmatched, internal_conflict, both_disagree}`,
  все 150 эталонных id размечены другими источниками (`bigvul_only`/`both_agree`/
  `diversevul_only`) и остаются как в v2. Отдельно посчитано согласие нового источника именно
  на эталонных 150 (не для замены, а для контроля): 146/150 = 97.33%, 4 расхождения (id
  71857, 66318, 29969, 53312, все три из `diversevul_only`) — обсуждение см. §3.
- Покрытие: **93.27% → 100.00%** (17 594 → 18 864 из 18 864). Остаток закрыт полностью.
- Другие кандидаты (`starsofchance/LineVul`, `DynaOuchebara/BigVul`, `mahdin70/cleaned_bigvul`,
  `pichulol/bigvul-megavul-clean-shuffled-10k`) не понадобились и не докачаны до конца —
  как только основной источник дал 100% покрытия точным совпадением по `unique_id`
  (максимально сильный сигнал, сильнее хеша), продолжать поиск других портов было
  нецелесообразно. Загрузки этих кандидатов остановлены (`kill`) после того, как стало ясно,
  что дальнейшая проверка ничего не может добавить к уже достигнутым 100%.

## 1. Что нашлось и почему это не обычный «порт LineVul»

Искали на HF по запросам `linevul`, `bigvul`, `big-vul`, `MSR20`. Среди результатов по
`linevul`:

| repo_id | что это |
|---|---|
| `realvul/LineVul_Test_Dataset` | 18 864 строки, колонки `unique_id, target, code`, train и test — идентичные копии друг друга |
| `zhouzl/LineVul_Test_Dataset_test` | не проверялся (см. ниже, нужды не было) |
| `zhouzl/linevultestdataset` | не проверялся |
| `starsofchance/LineVul` | LineVul train/val/test сплиты, репозиторий оказался ~4+ ГБ (вероятно, вместе с весами модели из replication package) — скачивание прервано, не понадобилось |
| `jasonhoang6201/linevul-08-26` | не проверялся |
| `jasonhoang6201/primevul-for-linevul` | подмножество PrimeVul, отфильтрованное под LineVul — уже покрыто PrimeVul из v2, отдельно не проверялся |

Первая же проверка `realvul/LineVul_Test_Dataset` дала не «ещё один похожий корпус», а
**точное совпадение по ключу `unique_id`**: колонка `unique_id` в этом HF-датасете — те же
числа, что в `case 3/3 кейс_датасет.csv` (73752, 54196, 169124, 109551, ... в той же
последовательности на первых строках). Проверено полным join по `unique_id` на все 18 864
строк обоих датасетов:

- 18 864 / 18 864 строк кейса 3 нашли пару по `unique_id` в `realvul/LineVul_Test_Dataset`.
- `code_case3 == code_realvul` дословно (без какой-либо нормализации) — **100%** (18864/18864).
- Нормализованный хеш (`sha256(re.sub(r'\s+', '', code))`) — тоже 100% совпадение, как и
  ожидалось при побайтовом совпадении.

Это означает: `realvul/LineVul_Test_Dataset` — не сторонний корпус, который случайно
пересёкся по каким-то функциям, а **прямая копия датасета кейса 3 с приклеенной колонкой
`target`**. Происхождение этой колонки со стороны HF не описано (README датасета — только
служебная секция `dataset_info`, без текстового описания и ссылок на источник). Точная причина
совпадения (утечка из более ранней версии датасета/бенчмарка, тот же исходный релиз, из
которого организаторы взяли `case 3/3 кейс_датасет.csv`, или что-то ещё) не установлена и не
может быть установлена по доступным метаданным — установлен только факт полного текстового
совпадения и высокая согласованность с независимо восстановленными в v1/v2 лейблами (см. §2),
этого достаточно для использования источника по той же методологии, что и раньше (BigVul/
DiverseVul/PrimeVul тоже принимались по согласию, а не по декларации о происхождении).

## 2. Проверка согласия (Задача 3) — прежде чем принимать

Тот же принцип, что в v2 (§2.1 того файла): не доверять источнику на слово, посчитать согласие
на пересечении с уже размеченными фрагментами.

| проверка | n | результат |
|---|---:|---|
| Согласие «как есть» с 17 594 уже размеченными (v2, `bigvul_only`+`both_agree`+`diversevul_only`+`primevul_corrected`+`ecwk_cvefixes2022`) | 17 594 | **99.43%** (17 493 согласий, 101 расхождение) |
| Согласие при инверсии поля (`1 - target`) | 17 594 | **0.57%** (101 согласие) |

Разница на два порядка (99.43% против 0.57%) однозначно показывает: направление поля **не**
перевёрнуто, флип не нужен — в отличие от PrimeVul в v2, где было наоборот
(0.26% как есть → 99.74% после флипа). Обе крайности (близко к 100% и близко к 0%) — это два
зеркальных исхода одной и той же проверки, ожидаемых при семантическом совпадении конвенции;
здесь совпадение прямое.

Разбивка 101 расхождения по источнику *существующей* разметки:

| match_source существующей записи | n расхождений | доля от размера группы |
|---|---:|---:|
| `diversevul_only` | 79 | 79 / 933 = 8.47% |
| `bigvul_only` | 16 | 16 / 9462 = 0.17% |
| `both_agree` | 6 | 6 / 6728 = 0.09% |
| `primevul_corrected`, `ecwk_cvefixes2022` | 0 | 0% |

Картина согласуется с уже задокументированным в v2 наблюдением (§2.1, §3 v2): DiverseVul
заметно шумнее BigVul по разметке на уровне отдельных функций. Уровень расхождения на
`bigvul_only`/`both_agree` (0.09–0.17%) — тот же порядок «естественного шума», что у PrimeVul
в v2 (22/8618 = 0.26%). Это не повод отвергать источник — 99.43% суммарного согласия
на 17 594 независимо (из других корпусов) размеченных фрагментах — сильный сигнал, сравнимый
с PrimeVul (99.74%) и заметно выше порога 95%, использованного в v2 как критерий приёмки.

## 3. Проверка эталонных 150 (обязательный пункт)

**Эталонные 150 (`out/bench/case3_eval_ids.txt`) не изменились**: они получили лейбл в v2 из
источников `bigvul_only`/`both_agree`/`diversevul_only`, и правило заполнения v3 трогает
только строки с `match_source ∈ {unmatched, internal_conflict, both_disagree}` — эталонные 150
в эту группу не входят ни одна. Проверено скриптом: **0 расхождений между v2 и v3** для этих
150 id, побайтово (все пять колонок).

Отдельно, как диагностика (не как основание для изменений), посчитано согласие нового
источника именно с текущими эталонными лейблами: пересечение — все 150 (все они есть в
`realvul/LineVul_Test_Dataset`, что ожидаемо при 100%-й идентичности датасета), согласие —
**146 / 150 = 97.33%**. 4 расхождения: id 71857, 66318, 29969, 53312 — все четыре текущий
лейбл получили из `diversevul_only`. Это соответствует наблюдению §2 (DiverseVul — самый
шумный из четырёх источников v2 по этой метрике, 8.47% несогласия против 0.09–0.17% у
BigVul-based источников), не выглядит как признак проблемы с новым источником. Эталонные
лейблы **не заменялись** этими 4 расхождениями — правило v3 не трогает уже размеченные строки
независимо от результата этой диагностики.

## 5. Воспроизводимость

```bash
hf download realvul/LineVul_Test_Dataset --repo-type dataset --local-dir <scratch>/linevul_realvul
```

Матчинг — прямой join по `unique_id` (не по хешу кода — хотя проверка нормализованным хешем
дала тот же результат, потому что код совпадает дословно). Лейбл кейса 3 = колонка `target`
без инверсии (направление подтверждено §2). Скачанный датасет не закоммичен — при повторном
запуске скачать заново и повторить join.

Датасет кейса 3 при этом ни разу не компилировался и не исполнялся — вся работа чисто
текстовая (join по `unique_id`, посимвольное сравнение строк, SHA-256 для контрольной
проверки), как и в предыдущих раундах.
