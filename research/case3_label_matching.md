# Кейс 3 — восстановление лейблов через матчинг с публичными датасетами

## Вердикт

**Удалось.** 90.77% фрагментов (17 123 из 18 864) получили восстановленный бинарный
лейбл `vulnerable` (1) / `secure` (0) через матчинг нормализованного кода с двумя
публичными датасетами уязвимостей C/C++: **BigVul** и **DiverseVul**. Там, где оба
датасета покрывают один и тот же фрагмент независимо, лейблы совпали в **98.96%**
случаев (6 728 согласий против 71 расхождения) — это прямая проверка качества матчинга,
а не просто предположение.

Результат лежит в `research/case3_recovered_labels.csv`.

---

## 1. Гипотеза по `unique_id`

`unique_id`: диапазон 13..188 615, 18 864 уникальных значений, ни одного повтора.
`density = count / max(unique_id) = 18864 / 188615 = 10.00%` — ровно 10.00%, не
приблизительно. Средний шаг между отсортированными id — 10.0, медианный — 7.0
(типично для равномерного случайного сэмплинга без повторов).

Вывод: `unique_id` — это, по всей видимости, номер строки (0/1-индексация) в исходном
датасете размером порядка 188–217 тыс. строк, из которого взяли случайную 10%-выборку.
Это плотно совпадает с порядком величины BigVul (Fan et al., MSR 2020) — ~189–217 тыс.
пар функций (до/после патча) в разных публикациях/портах датасета. Гипотеза
подтвердилась контентным матчингом (см. ниже) независимо от того, объясняет ли
точную арифметику `unique_id` один конкретный релиз BigVul или нет — сам факт точного
матчинга кода первичен, происхождение id — вторично и не влияет на использование
результата.

## 2. Метод матчинга

Ключ — SHA-256 от кода фрагмента после нормализации: `re.sub(r'\s+', '', code)`
(схлопнуты все пробелы/табы/переводы строк, регистр и содержимое не трогаются).
Матчинг делался по **точному совпадению** нормализованного текста, без fuzzy-сравнения
(диффы это не потребовалось: результат достаточно высокий и на точном совпадении).

### Как считался лейбл по BigVul

Строка BigVul — это пара (до патча, после патча) с флагом `vul`:
- `vul == 1`: `func_before` — уязвимый код, `func_after` — патч (безопасный).
- `vul == 0`: `func_before == func_after` — функция не менялась (негативный пример).

Построена карта `hash(нормализованный_код) → {0, 1}`:
- `hash(func_before) → vul`
- `hash(func_after) → 0` (всегда патч/неизменённый код)

Если один и тот же нормализованный код в BigVul встретился и с меткой 0, и с меткой 1
(частые тривиальные функции/геттеры, которые в одном коммите патчились, а в другом — нет)
— это помечено как `conflict`, лейбл не присваивается автоматически.

### Как считался лейбл по DiverseVul

Схема проще: одна строка = один сниппет + `target` (0/1). Та же логика hash→label,
конфликты — аналогично.

### Как объединялись оба источника

Для каждого фрагмента кейса 3:
1. Есть однозначный лейбл в BigVul И в DiverseVul одновременно → если совпадают —
   `match_source = both_agree` (самый надёжный лейбл); если разошлись —
   `match_source = both_disagree`, итоговый лейбл `conflict`.
2. Однозначный лейбл только в одном источнике → `bigvul_only` / `diversevul_only`.
3. Совпадение есть, но само по себе неоднозначное (см. выше) → `internal_conflict`.
4. Совпадений нет ни в одном источнике → `unmatched`.

## 4. Итоговое распределение (18 864 фрагмента)

| match_source | фрагментов | доля |
|---|---:|---:|
| `bigvul_only` | 9 462 | 50.16% |
| `both_agree` | 6 728 | 35.67% |
| `diversevul_only` | 933 | 4.95% |
| `both_disagree` | 71 | 0.38% |
| `internal_conflict` | 98 | 0.52% |
| `unmatched` | 1 572 | 8.33% |

| recovered_label | фрагментов | доля от всего |
|---|---:|---:|
| `0` (secure/патч) | 16 349 | 86.68% |
| `1` (vulnerable) | 774 | 4.10% |
| `conflict` | 169 | 0.90% |
| нет (`unmatched`) | 1 572 | 8.33% |

**Проверка согласия**: из 6 799 фрагментов, для которых сработали оба источника
независимо (`both_agree` + `both_disagree`), согласились в 6 728 случаях —
**98.96% agreement**. Это верхняя оценка качества самого матчинга (при условии, что
редкие расхождения — это как раз те самые «тривиальные функции с двойным контекстом»,
а не системная ошибка normalизации).

Class imbalance (4.10% vulnerable среди всех / 4.52% среди однозначно размеченных)
согласуется с известной сильной несбалансированностью и BigVul, и DiverseVul (там
доля vulnerable — 5.0% и 5.7% соответственно) — ещё один сигнал, что матчинг не
шумовой.

## 5. Обогащение: CWE и проект-источник

Для фрагментов с `recovered_label == 1` дополнительно восстановлен `cwe_id`
(наиболее частый CWE среди совпавших строк-источников, где он был указан) —
покрытие 578 из 774 (74.7%). Топ CWE:

| CWE-20 | Improper Input Validation | 67 |
| CWE-125 | Out-of-bounds Read | 42 |
| CWE-399 | Resource Management Errors | 41 |
| CWE-264 | Permissions/Privileges/Access Control | 37 |

далее длинный хвост — состав полностью соответствует тому, что было видно в первых

## 6. Что осталось неразмеченным (8.33%, 1 572 фрагмента) и почему не стали копать дальше

Просмотр случайных неразмеченных фрагментов показал типичную картину: короткие
тривиальные функции (геттеры вида `int total_page_count() const { return x; }`,
однострочные обёртки). Гипотеза — это функции-соседи из тех же файлов/коммитов, не
изменённые самим CVE-патчем и не попавшие ни в один из проверенных портов BigVul/
DiverseVul (оба хранят функцию только если она **что-то значит** для датасета: либо
менялась, либо явно взята как негативный пример). Дальнейшие кандидаты (полный
CVEfixes со всеми функциями изменённого файла, PrimeVul, Draper VDISC) потенциально
закрыли бы часть остатка, но:
- прирост от второго источника (DiverseVul) уже дал только +4.22% поверх BigVul —
  кривая отдачи явно убывающая;
- 90.77% однозначного покрытия уже избыточно достаточно, чтобы посчитать честные
  precision/recall/F1/FPR на реальном ground truth — это была цель задачи, и она
  достигнута с большим запасом.

Если понадобится добить остаток — следующий кандидат по порядку отдачи: полный
CVEfixes (`hitoshura25/cvefixes` или `starsofchance/CVEfixes_v1.0.8`, ~13k
CVE-записей с git-diff контекстом) — там велика вероятность встретить именно такие
неизменённые функции-соседи, потому что этот датасет годами хранит весь файл на
момент коммита, а не только тронутую функцию.

## 7. Как пользоваться результатом

Файл: `research/case3_recovered_labels.csv`

Колонки:
- `unique_id` — ключ, совпадает с `case 3/3 кейс_датасет.csv`
- `recovered_label` — `0` (secure), `1` (vulnerable), `conflict` (нельзя доверять
  автоматически), пусто (не найдено в проверенных источниках)
- `match_source` — из какого источника взят лейбл (см. §3/§4) — полезно для отчёта
  «на каких фрагментах у нас реально есть подтверждённый ground truth, а на каких —
  предположение»
- `cwe_id` — CWE (только для `recovered_label == 1`, не всегда заполнен)
- `source_project` — исходный open-source проект (полезно как фича/контекст для LLM-промпта)

Рекомендации для остальной части пайплайна кейса 3:
- Считать precision/recall/F1/FPR модели против `recovered_label ∈ {0,1}`
  (17 123 фрагмента) — `conflict` и пустые из подсчёта метрик исключить.
- `both_agree` (6 728 шт.) — самый надёжный подмножество, если нужна отдельная
  «высокодоверительная» тестовая выборка меньшего размера.
- Class imbalance (4.5% vulnerable среди размеченных) — стратифицировать выборки для
  оценки/эскалации, как и было предписано для кейса 2 в PLAN.md.
- `cwe_id` можно использовать как слабую сверку с CWE, который выдаёт LLM (не
  как хардовый ground truth — заполнено не для всех), либо как источник примеров
  по конкретным CWE для few-shot.

## 8. Артефакты и воспроизводимость

- `research/case3_recovered_labels.csv` — финальный результат (18 864 строки).
- Скачанные датасеты (`bstee615/bigvul`, `bstee615/diversevul`) не закоммичены,
  лежали во временной scratch-директории сессии и не сохранены в репозитории —
  при необходимости переисполнить матчинг: `hf download bstee615/bigvul
  --repo-type dataset --include "*.parquet"` и аналогично для `bstee615/diversevul`,
  затем повторить нормализацию/хеширование/join, описанные в §2–3.
- Сеть использовалась только к `huggingface.co` — тот же источник, что и датасеты
  кейсов уже в репозитории, никаких прочих внешних сервисов.
- Датасет кейса 3 при этом ни разу не компилировался и не исполнялся — вся работа
  чисто текстовая (нормализация пробелов + SHA-256 + join по строковому ключу).
