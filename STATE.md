| Конфигурация | P | R | F1 | FPR | n | Переносится на чужой код |

| ансамбль weighted | 0.857 | 0.360 | 0.507 | 0.030 | 150 | **нет** |

**ГЛАВНЫЙ ВЫВОД: корпусно-зависимые компоненты обваливаются в 0.000 кросс-проектно.**
logreg: F1 0.333 на Chrome при пуле со всеми проектами → 0.000 без Chrome в пуле.
Конфигурация B: 0.385 → 0.000. Причина: 89.3% ближайших соседей из того же проекта —
это узнавание проекта, а не обнаружение уязвимостей.

Следствие: ансамбль с F1 0.585 работает **только там, где есть размеченный корпус того же
происхождения**. На коде банка деградирует до чистой LLM. В отчёте писать честно.
Единственный переносимый путь — конфигурация A + скринер.

**Побочный результат для отчёта:** классический SAST на реальных CVE почти бесполезен —
flawfinder recall 18% при FPR 5%, сигнатурный триаж 10.5%.

## Известные ограничения и ловушки

- **Кейс 2: `doc_id` — позиция в ВЫБОРКЕ, а не в исходном parquet.** Сопоставление с эталоном
  по индексу исходного файла даёт мусорные метрики (F1 ~0.52 вместо 0.989). Эталон брать через
  `load_case2(split, n, seed)` с теми же параметрами, что и прогон. Ошибка уже совершена однажды.
- **Dry-run метрики кейса 3 бессмысленны.** Генератор заглушек в `core/llm.py` не может выдать
  `verdict="vulnerable"`, поэтому все dry-run цифры тождественны baseline «всё secure».
  Это ожидаемо, не баг.
- **Кейс 3 труден объективно, а не из-за промпта.** Фрагменты BigVul — реальные CVE из ядра
  Linux и Chrome, где уязвимость почти никогда не видна внутри одной функции: нужен контекст
  вызова и инварианты соседнего кода. Низкий recall ожидаем для любой модели.
- **Accuracy в кейсе 3 показывать нельзя.** При доле уязвимых 4.1% тривиальный baseline
  «всё secure» даёт 95.9%. Показываем только recall/precision/F1/FPR со сравнением к baseline.
- **Кейс 2: F1 0.984 подозрительно высок.** Датасет шаблонный, модель во многом ловит стилистику
  генератора. К защите нужны 10-15 инъекций, написанных руками, чтобы показать работу
  LLM-слоя вне распределения датасета. Не сделано.
- **Self-audit кейса 1 проверяет полноту ЗАМЕНЫ, а не полноту ОБНАРУЖЕНИЯ.** На вход подаются
  спаны наших детекторов, а не эталонные. Сильная версия (подать эталонные `spans`) даст
  утверждение «ни одна размеченная сущность не осталась в тексте» — работы минут на десять,
  не сделано.
- **Триаж кейса 3 — не фильтр.** Recall 10.5%. Использовать только как признак приоритета.
  Если в новой сессии возникнет идея «отсеять по триажу и сэкономить» — она уже проверена
  и отвергнута измерением.
- Инструмент записи блокирует имена файлов со словом `report` (и `findings.md` тоже) —
  писать такие файлы через Bash heredoc.
- Ключ DeepSeek в `.env`, `run.py` грузит его сам через `load_dotenv()`. Скрипты в `cases/*/`
  этого не делают — для них: `set -a && . ./.env && set +a && .venv/bin/python ...`
