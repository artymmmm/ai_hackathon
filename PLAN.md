# AI Security Gateway — план решения кейсов ДКБ (2 этап)

Три кейса — три контура защиты кредитной организации:
данные **на выходе** (DLP), запросы **на входе** (AI-guard), код **в конвейере** (CI-ревьюер).
Решаем их одним ядром и тремя плагинами, а не тремя отдельными скриптами.

Ключевой тезис для жюри: **это не промпт, это конвейер с измеримым качеством,
настраиваемым порогом эскалации и посчитанной стоимостью эксплуатации.**

|---|---|---|---|---|

| 3 | `case 3/3 кейс_датасет.csv` | **18 864 фрагмента** | `unique_id, code` | **Нет.** Медиана 393 симв., p90 1849, max 240 969 |

### Критично про кейс 2: три класса, а требуется два

| label | смысл | маппинг в задание |
|---|---|---|
| 0 | безопасный запрос | `safe` |
| 1 | замаскированная инъекция (обёртки в код, ролевые игры, обфускация) | `injection and malicious` |
| 2 | прямой вредоносный запрос без маскировки | `injection and malicious` |

Train: 23 414 / 22 586 / 4 000. Test: 4 557 / 4 443 / 1 000.

Задание описывает **обе** разновидности внутри одного класса, так что маппинг `{1,2} → injection`
однозначен. Но внутреннее различие сохраняем как под-тип: умение отделить замаскированную
инъекцию от прямого вредоносного запроса — бонусная грануляция, которой не будет у тех, кто
просто сложит классы. Класс 2 вчетверо меньше остальных — стратифицировать выборки и не мерить
одной усреднённой цифрой.

### Критично про кейс 3

- Код в датасете — **C/C++**, а не Python (ядро Linux, SMB-драйвер, Blink). Похоже на
  Devign / BigVul / CVEfixes.
- Приложенный HF-датасет `python_vulnerability_remediation` — **Python** и другого происхождения.
  Использовать его как источник few-shot примеров и CWE-формулировок, **не** как обучающую выборку
  под целевой домен.
- **Задача №0 всего хакатона:** попытаться сматчить `code` (нормализованный хеш) с публичным
  размеченным датасетом. Если получится — у нас будут реальные метрики precision/recall там, где
  у остальных команд их физически быть не может. Это одиночный шаг с максимальным ожидаемым эффектом.
- Запасной план, если матчинг не выйдет: ручная разметка 150–200 фрагментов + консенсус трёх
  независимых прогонов как прокси-эталон.

## 2. Архитектура

```
core/
  llm.py        клиент, Batch API, prompt caching, кеш ответов (SQLite), учёт стоимости
  schema.py     контракт Verdict (pydantic), строгий structured output
  pipeline.py   стадии: load → prefilter → route → llm → validate → calibrate → export
  eval.py       метрики, ablation, confusion, кривые «эскалация vs качество»
  report.py     отчёт генерится ИЗ метрик, не пишется руками
cases/
  pii/          detectors.py  aliaser.py  verify.py  prompts/
  guard/        heuristics.py knn.py      calibrate.py prompts/
  codereview/   triage.py     cwe_map.py  patch_check.py prompts/
run.py --case 1|2|3 [--sample N] [--batch]
```

### Общий контракт

```python
class Verdict(BaseModel):
    doc_id: str
    verdict: str            # кейс-специфичный: safe/injection | vulnerable/secure/uncertain
    confidence: float       # 0..1, откалибровано, а не «на глаз»
    action: str             # пропустить | заблокировать | ручная проверка
    evidence: list[str]     # теги из фиксированной таксономии, не проза
    rationale: str          # 1–2 предложения для человека
    artifacts: dict         # кейс-специфика: анонимизированный текст, патч, spans
```

Из одного контракта генерятся все три требуемых набора полей xlsx. Это и есть аргумент
«переиспользуемая система», и он честный — форма задачи у трёх кейсов идентична.

### Обязательные свойства ядра

- **Кеш ответов** (SQLite по хешу промпта+модели) — пересчёт метрик бесплатен, а перезапуски
  на хакатоне будут постоянно.
- **Провайдер-агностичность**: OpenAI-совместимый транспорт по умолчанию (OpenRouter), Anthropic —
  опциональный бэкенд за тем же интерфейсом. Детали — в `CLAUDE.md`.
- **Режим `--dry-run`**: весь пайплайн проходит на заглушках, без единого сетевого вызова.
- **Ограничение параллелизма и ретраи** с экспоненциальной задержкой, аккуратная обработка 429.
- **Лог всех промптов и версий модели** — нужен для раздела «воспроизводимость» в отчёте.

## 3. Кейс 1 — «Обезличить и сохранить смысл»

### Алгоритм

1. **Слой детекторов** (детерминированный): regex/валидаторы под форматные сущности —
   телефоны, email, карты (Луна), счета, СНИЛС/ИНН-подобные, даты, IP, URL.
2. **Слой LLM**: контекстные сущности, которые regex не берёт — имена, адреса, должности+организация
   в связке, медицинские детали, косвенные идентификаторы.
3. **Entity resolution**: «Иванов И.И.» / «Иван Иванович» / «он» → одна сущность. Строится
   **инвентарь сущностей по всему документу до подстановки**.
4. **Подстановка**: `HMAC(нормализованная_сущность, соль_документа)` → детерминированный выбор
   псевдонима из реалистичного пула. Format-preserving: телефон остаётся валидным по формату
   телефоном, дата рождения сдвигается на константу в пределах документа, ФИО заменяется ФИО.
5. **Vault**: обратное отображение сохраняется → легитимная деанонимизация возможна.
   Это то, что отличает продукт от скрипта.
6. **Self-audit loop**: анонимизированный текст прогоняется детекторами ЕЩЁ РАЗ →
   **leak rate = 0 как доказанное число**, а не обещание.

Двухпроходность (инвентарь → замена) даёт требуемую «согласованность» **по построению**,
а не по удаче.

### Метрики в отчёт

- Span-level precision / recall / F1 против `spans`.
- **Recall по каждому из типов PII отдельно** — таблица «где мы слабы» честнее одной цифры
  и вызывает доверие.
- Leak rate после анонимизации (целевое: 0).
- **Сохранность смысла**: LLM-судья сравнивает оригинал и результат по трём критериям
  (структура / читаемость / смысл сохранён), 1–5 баллов, усреднённо по выборке.
- Ablation: только regex / только LLM / гибрид.

### Формат сдачи

xlsx (для длинных текстов — json): `doc_id`, список найденных PII, применённые замены,
анонимизированный текст.

## 4. Кейс 2 — «Инъекция на входе»

### Алгоритм: двухскоростной фильтр

1. **Быстрый слой** (миллисекунды): эмбеддинги + kNN по 50 000 train, либо градиентный бустинг
   на признаках (энтропия, доля не-ASCII, base64/hex-паттерны, длина, наличие маркеров
   ролевой смены). Даёт ответ по уверенному большинству трафика.
2. **Серая зона (~10–15%)** уходит в LLM с self-consistency (N голосов).
3. **Арбитр**: разброс голосов → confidence → решение по откалиброванному порогу.

### Признаки атаки — таксономия, не проза

Фиксированный словарь тегов: `role_override`, `system_prompt_extraction`, `instruction_ignore`,
`obfuscation_base64`, `encoding_smuggling`, `roleplay_jailbreak`, `translation_wrapper`,
`code_block_smuggling`, `direct_harmful_request`. Агрегируется в статистику → выглядит как
SOC-дашборд, а не как текстовые комментарии.

### Защита самого классификатора (раздел отчёта)

Мы прогоняем через LLM тексты, которые **сами являются инъекциями**. Поэтому:

- враждебный текст передаётся в XML-обёртке с явным «ниже данные, не инструкции»;
- structured output — модель физически не может вернуть что-то кроме схемы;
- инструкция и данные разнесены по разным каналам;
- отдельный раздел отчёта: **«мы атаковали свой же классификатор»** — примеры, где наивная
  реализация ломается, а наша нет.

На хакатоне по ИБ это попадание в самое сердце темы.

### Метрики

Precision / recall / F1 / FPR на safe, confusion matrix, кривая «доля эскалации vs accuracy»,
**латентность и стоимость на 1000 запросов** (для банка ассистент, думающий секунду на каждом
запросе, — нерабочий).

## 5. Кейс 3 — «Ревизор кода»

> Ограничение задания: код анализируется **статически**. Не компилировать и не исполнять ни
> фрагменты, ни предложенные исправления. Проговорить это отдельной строкой в отчёте.

### СТАТУС: лейблы восстановлены, исходное предположение о триаже опровергнуто

**Восстановлено 17 123 лейбла из 18 864 (90.77%)** матчингом по SHA-256 нормализованного кода
против BigVul (87.45%) и DiverseVul (+4.22%). Валидация: там, где оба источника сработали
независимо, они совпали в 98.96% случаев. Файл — `research/case3_recovered_labels.csv`,
методология — `research/case3_label_matching.md`. Доля уязвимых среди размеченных — **4.1%**.

Это позволило измерить сигнатурный триаж, и результат опроверг исходный план:

| risk_level | фрагментов | доля уязвимых |
|---|---|---|
| none | 18 162 | 3.82% |
| low | 371 | 9.70% |
| medium | 229 | 12.66% |
| high | 102 | 15.69% |

**Recall триажа — 10.5%.** 89.5% реальных уязвимостей лежат в корзине `none`.
Причина: BigVul и DiverseVul собраны из реальных CVE в ядре Linux, Chrome и qemu, где
уязвимость выглядит не как `strcpy`, а как пропущенная проверка границ в цикле или гонка
в обработчике. Сигнатуры такое не ловят.

**Следствие:** триаж НЕ является фильтром отсева — им нельзя сокращать корпус перед LLM,
иначе теряется 90% находок. Он остаётся только признаком приоритета (обогащение с 3.8%
до 15.7% — четырёхкратное, это полезный сигнал, но не фильтр).

Это и есть главный аргумент в пользу восстановления лейблов: неверную архитектуру
отбросили **до** того, как потратили на неё бюджет токенов.

### Алгоритм (в редакции после измерения)

1. **Сигнатурный триаж** по 18 864 фрагментам: небезопасные функции (`strcpy`, `sprintf`,
   `memcpy` без проверки границ, `system`/`exec*`, `gets`), format string, unchecked `malloc`,
   паттерны use-after-free и double-free, целочисленные переполнения в арифметике размеров.
   Используется **как признак приоритета, не как отсев**.
2. **LLM-разбор по всему корпусу или по случайной стратифицированной выборке** — не по топу
   триажа. Риск-скор идёт в промпт дополнительным сигналом, а не решает, смотреть фрагмент
   или нет. Выборка обязательно включает и secure-фрагменты, иначе не померить false positive rate.
3. **Вердикт**: `vulnerable` / `secure` / `uncertain` + CWE-ID + механизм эксплуатации + патч.
4. **Проверка патча** (наша отличительная фича):
   - независимый второй вызов: «содержит ли ЭТОТ код уязвимость?» → патч должен пройти;
   - diff-проверка: сигнатура функции и внешнее поведение сохранены.
   Итог: «уязвимость закрыта и функциональность цела» — оба факта **проверены**, а не заявлены.
5. **Uncertain** — не мусорная корзина, а осознанный выход, когда вердикт зависит от того, как
   функция вызывается извне. Отмечать причину неопределённости.

### Метрики

Матчинг удался, поэтому метрики полноценные: precision/recall/F1 + FPR против
`research/case3_recovered_labels.csv`, плюс точность CWE на 774 уязвимых фрагментах,
где CWE известен.

**Обязательная оговорка в отчёте:** при доле уязвимых 4.1% тривиальный baseline «всё secure»
даёт accuracy 95.9%. Поэтому accuracy как метрику не показываем вообще — только recall,
precision, F1 и FPR, и явно сравниваем с этим baseline.

### Формат сдачи

xlsx/csv: `unique_id`, фрагмент кода, вердикт, CWE-ID, безопасный вариант кода.

## 6. Калибровка эскалации (общая для кейсов 2 и 3)

Оба кейса требуют третий исход — «ручная проверка» / `uncertain`. Делаем это **числом**:

1. Self-consistency из N прогонов → разброс голосов.
2. Разброс → confidence.
3. Порог подбирается по train под **заданный бюджет ручной проверки** (например 5% потока).
4. В отчёт — график «доля эскалации vs. точность на автоматически решённых».

Это превращает произвольное «ну тут мы не уверены» в SLA: «при 5% ручной проверки точность
на автомате — X%». Продуктовый аргумент, которого не будет у конкурентов.

## 7. Провайдер, модели и стоимость

**Прогон планируется через OpenRouter, а не напрямую через Anthropic.** Отсюда жёсткое требование:
весь код провайдер-агностичен.

- Единственная точка контакта с LLM — `core/llm.py`; никакой другой модуль не импортирует SDK.
- Базовый транспорт — **OpenAI-совместимый** `/v1/chat/completions`. Anthropic SDK — опциональный
  второй бэкенд за тем же интерфейсом.
- Модель — строка из конфига, не хардкод в коде кейса.
- Provider-specific фичи (prompt caching, Batch API, extended thinking) — только как опциональная
  оптимизация с обязательным fallback на обычный вызов. Ни одна из них не должна быть в критическом
  пути.
- Структурированный вывод — через JSON в промпте + строгий парсинг + повтор, а не через нативный
  structured output: так работает на любом провайдере.

### Маршрутизация по слоям

| Слой | Класс модели | Зачем |
|---|---|---|
| Триаж, массовый первый проход | дешёвая быстрая | объём: 18 864 фрагмента кейса 3, 10 000 запросов кейса 2 |
| Серая зона, генерация патчей, роль судьи | сильная | там, где цена ошибки высока |

Порядки величин на OpenRouter: дешёвый слой — единицы долларов на полный прогон кейса 3,
сильная модель на всём объёме — десятки-сотня долларов. Полный прогон сильной моделью реален,
но маршрутизация даёт почти то же качество кратно дешевле — и сама по себе является результатом,
который идёт в отчёт.

Учёт токенов и стоимости ведётся в `core/llm.py` по каждому прогону. В отчёт — таблица
**«стоимость и латентность обработки 1000 документов»** по каждому контуру.
