# Кейс №3 «Ревизор кода» — отчёт

*Черновик. Заполнено всё, кроме итоговых чисел полного прогона — они помечены `[ПОСЛЕ ПРОГОНА]`.*

## Что система находит — на настоящей уязвимости

Фрагмент из корпуса, `unique_id 181061` — функция разбора L2TP-пакета из tcpdump.
Эталон: уязвима. Это реальная CVE, а не учебный пример.

```c
l2tp_accm_print(netdissect_options *ndo, const u_char *dat)
{
const uint16_t *ptr = (const uint16_t *)dat;
uint16_t val_h, val_l;

ptr++;		/* skip "Reserved" */

	val_h = EXTRACT_16BITS(ptr); ptr++;
	val_l = EXTRACT_16BITS(ptr); ptr++;
ND_PRINT((ndo, "send=%08x ", (val_h<<16) + val_l));

val_h = EXTRACT_16BITS(ptr); ptr++;
val_l = EXTRACT_16BITS(ptr); ptr++;
ND_PRINT((ndo, "recv=%08x ", (val_h<<16) + val_l));
}
```

Что вернуло решение — **вердикт `vulnerable`, CWE-125 «Out-of-bounds Read», уверенность 0.9**,
и заполненный разбор, который промпт требует ДО вердикта:

> **Что функция предполагает о входах:** что `dat` указывает на буфер, содержащий как минимум
> 10 байт (5 16-битных слов): одно пропускается как Reserved, затем читаются 4.
>
> **Указатели с риском NULL:** `dat` не проверяется на NULL перед разыменованием; `ptr`
> производный от него, тоже не проверяется.
>
> **Непроверенные длины:** явной проверки длины буфера нет вовсе. Функция читает 10 байт без
> проверки, что буфер такого размера.
>
> **Механизм эксплуатации:** если вызывающий код передаст буфер меньшего размера — например,
> из-за усечённого пакета — произойдёт чтение за пределами выделенной памяти, что может
> привести к утечке информации или краху.

И предложенный безопасный вариант:

```c
l2tp_accm_print(netdissect_options *ndo, const u_char *dat)
{
    const uint16_t *ptr = (const uint16_t *)dat;
    uint16_t val_h, val_l;

    if (dat == NULL)
        return;

    ptr++;      /* skip "Reserved" */

    if (ndo->ndo_snapend - (const u_char *)ptr < 8)
        return;

    val_h = EXTRACT_16BITS(ptr); ptr++;
    ...
}
```

Стоит заметить, что патч использует `ndo->ndo_snapend` — **правильную для tcpdump границу
захваченных данных**, а не выдуманную проверку. Модель опознала конвенцию проекта по одному
фрагменту.

Патч дальше проходит три статические проверки (сигнатура функции сохранена, функциональность
на месте, паттерн триажа исчез) и независимое второе мнение: тот же вопрос «есть ли здесь
уязвимость», заданный по патченному коду, **без упоминания, что это патч и что было раньше**.
Расхождение уводит находку в `manual_review`.

**Код при этом не компилировался и не исполнялся** — ни исходный, ни патч. Все проверки
текстовые.

### И то, что мы считаем ложной тревогой

Честности ради — вот типичная запись из наших 46% ложных срабатываний:

```c
void buffer_advance(Buffer *buf, size_t len)
{
    memmove(buf->buffer, buf->buffer + len, (buf->offset - len));
    buf->offset -= len;
}
```

Вердикт: `vulnerable`, CWE-119. Обоснование: *«Отсутствует проверка `len` против `buf->offset`,
что при `len > offset` приводит к целочисленному переполнению `size_t` и последующему
переполнению буфера в `memmove`.»* Эталон говорит «безопасно».

Формально мы ошиблись. По существу — замечание верное: `size_t` действительно переполнится,
и защиты в функции нет. Разметка помечает фрагмент безопасным потому, что это починенная
половина CVE-пары, а не потому, что код безупречен. Значительная часть нашей «потерянной
точности» выглядит именно так, и это стоит держать в голове, читая precision 0.541.

## Какой инструмент использовался

Один вызов LLM на фрагмент: `deepseek-chat` через OpenAI-совместимый API, промпт
высокочувствительного скринера плюс короткий блок-чек-лист. Плюс статические проверки патча
и независимое второе мнение по нему. Именно эта конфигурация подключена в боевом пути
`run.py --case 3` — не экспериментальная ветка, а то, что реально запускается.

**Код из датасета не компилировался и не исполнялся** — ни фрагменты, ни предложенные нами
исправления. Требование задания соблюдено буквально: анализ только текстовый. Использованный
«статический анализатор» — regex-сканер по тексту, а не компилятор.

## Промпт

Полный текст — `cases/codereview/reviewer_configs.py`, константа `SYSTEM_PROMPT_SENSITIVE`.
Ключевые решения в нём:

- **Режим скринера, а не финального судьи.** Явно сказано, что ложная тревога дешевле
  пропуска: пропущенная уязвимость в системном коде стоит эксплуатации в проде, лишняя
  проверка стоит нескольких минут ревьюера.
- **Обязательный разбор до вердикта.** Модель заполняет три поля прежде, чем решить:
  что функция предполагает о входах, какие указатели могут быть NULL, какие длины
  используются без проверки. Вердикт обязан следовать из них, а не наоборот.
- **Защита от инъекции через анализируемый код.** Содержимое тега `<code_fragment>` объявлено
  данными; текст внутри, похожий на команду, не меняет роль и формат ответа.
- **Три исхода, как требует задание:** `vulnerable`, `secure`, `uncertain` — последний для
  случаев, где решение зависит от внешнего контекста вызова.

## Краткий алгоритм

```
фрагмент C/C++
  ├─ сигнатурный триаж             → необязательная подсказка в промпт (не фильтр)
  ├─ LLM, один вызов               → вердикт, CWE, механизм эксплуатации, патч
  ├─ статические проверки патча    → сигнатура сохранена? функциональность на месте?
  ├─ второе мнение по патчу (LLM)  → «содержит ли ЭТОТ код уязвимость?»
  └─ расхождение ⇒ manual_review, доверие понижено
```

Триаж намеренно **не** используется как фильтр-отсев: его recall против восстановленной
разметки — 9.2% на полном корпусе, отсев по нему потерял бы девять уязвимостей из десяти.

## Результаты

Эталонный набор — 600 фрагментов (200 уязвимых / 400 безопасных), σ(F1) ≈ 0.03.

| конфигурация | precision | recall | F1 | FPR |
|---|---|---|---|---|
| базовый промпт | 0.673 | 0.165 | 0.265 | 0.040 |
| **поставочная конфигурация** | **0.541** | **0.300** | **0.386** | **0.128** |

**Полный прогон:** `[ПОСЛЕ ПРОГОНА]`. Смета: 18 864 фрагмента целиком, около 45 минут при
64 потоках, **$10.25** с учётом второго мнения по патчам.

### Операционное прочтение — важнее F1

В бинарных метриках исход `uncertain` засчитан как «безопасно», но в жизни он уходит человеку.
Реальная картина: решение доводит до человека **88% уязвимостей** ценой ручного просмотра
**77% чистого кода**. Как автоматический фильтр это слабо, как приоритизатор очереди на
ревью — работает. Задание прямо предусматривает `uncertain` для ручной проверки, и решение
этим пользуется, а не прячет неуверенность в бинарный вердикт.

## Почему F1 0.386, а не 0.9 из статей

Это главный вопрос к кейсу, и ответ у нас измеренный, а не риторический.

**Заявленные на этом корпусе F1 0.91–0.92 получены на случайном сплите.** Точность меток
класса «уязвимо» у самого BigVul по двум независимым ручным аудитам — 25% и 54%. На PrimeVul
те же архитектуры падают до 0.18–0.21 только от честных меток, дедупликации и хронологического
сплита. Честный коридор для LLM без дообучения — 0.13–0.54; мы в его середине.

**Мы проверили это на своих данных.** Корпусно-зависимые методы дают высокие числа внутри
распределения и ноль за его пределами:

| подход | F1 в распределении | F1 на другом проекте |
|---|---|---|
| logreg по TF-IDF | 0.500 | **0.000** |
| retrieval ближайших размеченных примеров | 0.385 | **0.000** |
| ансамбль корпусных методов | 0.585 | деградирует до чистой LLM |
| **наше решение** | **0.386** | переносится |

Причина измерена: 89.3% ближайших соседей приходят из того же проекта — это узнавание проекта,
а не обнаружение уязвимости. Заказчику нужен ревьюер для его собственного репозитория,
поэтому в поставку идёт менее эффектная, но работающая конфигурация.

### Мы проверили это на дообученной модели — своими руками

Взяли готовый чекпойнт `mahdin70/CodeBERT-PrimeVul-BigVul` (CodeBERT, дообученный на слиянии
BigVul и PrimeVul — то есть на происхождении нашего же корпуса). Выбран он потому, что это
единственный найденный кандидат, у которого **опубликован обучающий сплит** — иначе проверить
утечку было бы невозможно в принципе.

**Проверка утечки: 227 из 600 наших эталонных фрагментов (37.8%) модель видела при обучении.**
Сверка по MD5 нормализованного тела функции (убраны комментарии и пробельные символы) против
124 780 строк её обучающего сплита.

| замер на наборе 600 | precision | recall | F1 | FPR |
|---|---|---|---|---|
| дообученная, порог по умолчанию 0.5 | 0.940 | 0.235 | **0.376** | 0.008 |
| дообученная, порог подобран под наш FPR 0.128 | 0.669 | 0.515 | **0.582** | 0.128 |
| **наше решение** | 0.541 | 0.300 | **0.386** | 0.128 |

Читать это надо в три слоя.

**Слой первый: на своём пороге дообученная модель не лучше нас.** При штатном пороге 0.5 она
даёт F1 0.376 против наших 0.386 — вровень, хотя рабочая точка совсем другая: она почти не
ошибается на чистом коде (FPR 0.008), но находит лишь 23.5% уязвимостей.

**Слой второй: 0.582 получены подбором порога по нашим же лейблам.** Это законный приём для
сравнения при равном FPR, но он использует разметку оценочного набора, то есть даёт модели
преимущество, которого в бою у неё нет.

**Слой третий, главный: разрыв держится на запоминании.** Разделив тот же прогон по признаку
утечки при одном и том же пороге:

| подмножество | дообученная модель | наше решение |
|---|---|---|
| 227 фрагментов, которые модель видела при обучении | F1 **0.703** | — |
| 373 фрагмента, которых она не видела | F1 **0.450** | F1 **0.353** |

На незнакомом коде преимущество составляет 0.097 при σ(F1) около 0.045 на этом подмножестве —
примерно 2σ, то есть эффект реальный, но скромный. И это **вдвое ниже** заявленных в литературе
0.91–0.92 для дообученных моделей на этом корпусе.

**Вывод для заказчика.** Дообучение даёт прирост, но (а) намного меньший, чем обещают статьи,
(б) держащийся в значительной части на том, что модель уже видела эти функции, и (в) не
решающий задачу целиком: бинарный классификатор выдаёт только вердикт, а задание требует ещё
тип CWE, механизм эксплуатации и исправленный код. Поэтому дообученная модель уместна как
дополнительный сигнал, а не как замена ревьюера.

## Как мы к этому пришли: девять отвергнутых подходов

Поставочная конфигурация — это один вызов LLM с чек-листом. Выглядит скромно, и стоит
рассказать, что мы пробовали до неё, потому что почти всё оказалось хуже. Все числа — на
наборе 600, где σ(F1) ≈ 0.03; значимым считали разрыв больше 0.06.

**Состязательный суд: прокурор, защита, судья — F1 0.076.** Идея красивая: один вызов ищет
уязвимость, второй её опровергает, третий судит. Мы потратили на неё 2.44 миллиона токенов и
получили катастрофу — **из 50 уязвимостей судья признал две**. Защита оказалась слишком
убедительной: на любой найденный дефект она находит контекст, в котором он безвреден, а судья
предпочитает оправдать. Абляция «суд без защиты» ничего не изменила: сама роль судьи уже
склоняет к оправданию. Урок дорогой и полезный — состязательность в анализе кода работает
против нас, потому что доказать безопасность фрагмента риторически всегда легче, чем опасность.

**Критик поверх вердикта — F1 0.265.** То же самое в миниатюре: второй вызов перечитывает
рассуждение первого и говорит, согласен ли. Recall упал с 0.42 до 0.18 — критик систематически
оправдывает. Когда мы применили критика только к корзине `uncertain`, получилось 0.541, то есть
ровно вровень с первой ступенью: пользы ноль.

**Каскад с голосованием: +0.004 при σ 0.03.** Единственная надстройка, которая не сделала хуже.
Фрагменты из корзины `uncertain` шли на вторую ступень, где пять сэмплов голосовали за
форсированный бинарный вердикт. Прирост неотличим от нуля, зато цена — 75% стоимости полного
прогона ($94.61 против $23.86) и падение precision с 0.540 до 0.512. Отвергнуто по цене,
а не по качеству.

**Форсированный бинарный вердикт — 0.279.** Убрали право сказать «не уверен», ожидая, что
модель начнёт решать. Она начала уходить в `secure`: recall упал вдвое. Право на неуверенность
в этой задаче — не слабость промпта, а несущая конструкция.

**«Пометить всё уязвимым» даёт 0.500.** Это не подход, а планка: если читать `uncertain` как
`vulnerable`, получается 0.499 — то есть тривиальное «подозревать всех» даёт столько же,
сколько наше правило. Мы это посчитали и записали, потому что без такой планки любые 0.4
выглядят достижением.

**Смена модели: qwen3-30b 0.245, GigaChat-2-Max 0.209.** Второй результат ниже базовой линии
«всё secure». Дешёвая модель здесь не эквивалент дорогой.

**Декомпозиция рассуждения на два вызова — 0.297** против контроля 0.299 на том же провайдере.
Разделение «сначала опиши код, потом суди» не дало ничего.

Общий вывод, который стоит вынести отдельно: **второй проход помогает только когда форсирует
решение по неопределённым фрагментам; любая ролевая надстройка поверх готового вердикта его
размывает.**

## Честное признание про блок знаний

Мы называли CWE-карточки и правила SEI CERT retrieval-слоем. Проверка это опровергла:

- сигнатурный триаж не срабатывает у **96.3% корпуса**, и все эти фрагменты получают один и
  тот же фолбэк-набор CWE;
- поэтому блок правил принимает на 600 фрагментах всего 8 различных значений, одно покрывает
  96.3% — константная строка на 510 символов при медиане кода 466;
- зашитая наглухо строка воспроизводит «динамический» подбор: 0.373 против 0.386.

Развилка развела информацию и рамку: без блока 0.291, пять правил про **оформление кода**
(отступы, именование) 0.338, одна фраза без правил 0.349, правила SEI CERT 0.373. Блок нужен
(+0.082 над пустым, выше шума), но содержание безразлично. **Работает рамка, а не знание** —
и мы не выдаём промптовый нажим за таргетированный RAG.

## Оговорка к метрике CWE

Восстановленная разметка типа слабая: CWE проставлен лишь у 56.9% уязвимых фрагментов, ещё
464 значения стоят на безопасных (починенная половина CVE-пары унаследовала CWE своего CVE),
и лишь 35.5% значений — конкретные слабости, тогда как 21.2% — категорийные узлы, которые
MITRE прямо запрещает использовать для маппинга. Поэтому низкая CWE accuracy — на существенную
часть свойство эталона: если золото говорит CWE-399 «Resource Management Errors», а модель
отвечает CWE-416 «use-after-free», она права и точнее, но засчитывается ошибка.

## Побочный результат, полезный заказчику

Классический статический анализ на реальных CVE почти бесполезен: flawfinder даёт recall 18%
при FPR 5%, сигнатурный триаж — 9.2% на полном корпусе. Это аргумент за LLM-ревьюера,
а не против него.

## Ограничения, которые честно признаём

- Разметка восстановлена, а не выдана организаторами: найден источник, где текст и
  идентификаторы совпадают побайтово со всеми 18 864 фрагментами. Это надёжный ключ,
  но не золотой стандарт, размеченный руками.
- Эталонный набор содержит 33% уязвимых, а корпус — 5.59%. На сбалансированной выборке F1
  всегда выше, и наши 0.386 нельзя переносить на прод-распределение без пересчёта.
- Дальнейший рост на промптовом уровне исчерпан: девять проверенных гипотез не дали ничего
  выше шума. Следующий шаг — дообучение, что выходит за рамки задания и бюджета.

Три решения тимлида определили результат:

1. **Строить переиспользуемую систему, а не три скрипта.** Форма задачи у всех трёх кейсов
   одна: поток записей → структурированный вердикт → xlsx + отчёт. Значит ядро (`core/`)
   пишется один раз, а кейсы становятся плагинами к нему.
2. **Не привязываться к вендору.** Единственная точка сетевого вызова — `core/llm.py`,
   протокол OpenAI-совместимый, модель задаётся строкой конфигурации. За время работы решение
   прогонялось на девяти моделях четырёх провайдеров без единой правки кода кейсов.
3. **Жёсткие границы владения файлами.** Каждый агент пишет только в свою зону; общий контракт
   `Verdict` в `core/schema.py` не меняется в одностороннем порядке. Это позволило держать
   четырёх исполнителей в одном репозитории без конфликтов.

Дисциплина, которая держала качество: **любое утверждение о качестве подкреплено числом,
посчитанным скриптом и лежащим в файле.** Результат агента истиной не считался — числа
перепроверялись координатором по артефактам, а не по пересказу. Именно так были пойманы
собственные ошибки: заниженный на 0.02 F1 кейса 1 (мерили на детекторах с лишними ложными
срабатываниями), несуществующая десятикратная разница в скорости провайдеров и «RAG»,
оказавшийся константной строкой.
