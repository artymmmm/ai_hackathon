# Кейс 1 — обезличивание PII/PHI с сохранением смысла

Ключей LLM нет, живые вызовы запрещены. Все цифры ниже — реальный прогон детерминированного
слоя на `case 1/data/test-00000-of-00001.parquet` (выборка 2000 документов, `seed=42`,
`.venv/bin/python cases/pii/evaluate.py --n 2000`), не оценка на глаз.

## 1. Что в данных (разведка)

100 000 train + 100 000 test документов, `spans` — точная span-level разметка, **55 типов**
PII/PHI. На выборке 3000 документов (test) распределение (полная таблица в разделе 4):

- 5 самых частых типов: `first_name` (2590), `date` (2139), `last_name` (1854),
  `company_name` (1660), `email` (1573).
- В среднем **8.5 PII-сущностей на документ**.
- Локали: 50 000 `us` / 50 000 `intl` (примерно поровну).
- Критичное наблюдение для архитектуры детекторов: **ровно половина** всех PII-упоминаний в
  датасете (8575 из 17 168 на выборке 2000 документов) относится к типам без устойчивого
  формата — имена, гео-названия, свободная демография, occupation. Их **в принципе нельзя**
  поймать регэкспом надёжно; это жёсткая верхняя граница recall детерминированного слоя,
  а не недоработка. Вторая половина (35 типов) — форматные сущности, для которых регэкс —
  правильный инструмент.
- Второе наблюдение, изменившее реализацию: **синтетические номера карт в датасете почти
  никогда не проходят проверку Луна** (только 10 из 63 на выборке 500 — ~16%, то есть на уровне
  случайности). Это не настоящие карты, а случайные цифры «под формат» — Луна не используется
  как фильтр в `detectors.py`, только длина/группировка.
- Третье наблюдение: числовые ID-поля (`account_number`, `customer_id`, `employee_id`,
  `medical_record_number`, `national_id`, `tax_id`, `ssn`...) **визуально неотличимы друг от
  друга по значению** — все просто цифро-буквенные строки разной длины. Единственный надёжный
  сигнал — подпись поля перед значением ("Account Number:", "SSN:", "the employee ID is").
  Проверено на выборках по каждому типу (см. `detectors.py`, докстринг раздела CONTEXT) — во
  всех случаях контекст предшествует значению, это и определило архитектуру контекстных
  детекторов.

## 2. Архитектура

```
detectors.py   детерминированный слой: STANDALONE (формат сам себя выдаёт) + CONTEXT
               (формат неотличим без подписи поля) + даты/время
aliaser.py     инвентарь → HMAC-псевдоним → одна согласованная подстановка → vault
verify.py      self-audit: детекторы повторно на анонимизированном тексте
evaluate.py    span-level precision/recall/F1 против эталона, разбивка по типам
prompts/       промпт LLM-слоя для контекстных типов (не вызывается — нет ключей)
__init__.py    PLUGIN для core.pipeline (run.py --case 1)
```

### 2.1 Детекторы (`detectors.py`)

Два класса, оба обязательны для честного покрытия:

- **STANDALONE** — сущность узнаётся по одной форме без контекста: email, URL, IPv4/IPv6, MAC,
  номер карты (по длине/группировке цифр, без Луна — см. выше), VIN, SWIFT/BIC, UUID,
  координаты, ISO-datetime.
- **CONTEXT** — сущность выглядит как произвольная цифро-буквенная строка и узнаётся **только**
  по фразе-подписи перед ней (`<фраза>[:,]? <значение>` или `<фраза> is/was <значение>`):
  account_number, customer_id, employee_id, medical_record_number,
  health_plan_beneficiary_number, national_id, tax_id, certificate_license_number, ssn,
  bank_routing_number, pin, cvv, api_key, password, device_identifier, biometric_identifier,
  license_plate, postcode, fax_number, phone_number (с подписью), http_cookie, unique_id.
- Отдельно — **даты**: единый паттерн дат, лейбл `date_of_birth` присваивается, если в 30
  символах перед датой встречается "born"/"birth"/"dob", иначе `date`.

Порядок применения фиксированный и защищает от двойной разметки (более специфичный детектор
занимает диапазон первым, остальные его не трогают) — например `mac_address` идёт **перед**
`ipv6` (общий паттерн IPv6 иначе перехватывает MAC-адреса), а `phone_number`-fallback идёт
**после** всего контекстного слоя (иначе он успевает съесть SSN/fax до того, как более
специфичный контекстный детектор до них доберётся). Оба бага пойманы прогоном на реальных
данных, а не придуманы заранее.

**Регексы, обнаруженные ловушки (задокументированы в коде, не только здесь)**:
- Нежадный разрыв `[^\n]{0,20}?` между подписью поля и значением сам по себе матчит
  ближайшее слово-связку ("is", "was") как "значение" — потому что движок регэкспа
  останавливается на первом успешном совпадении, а не на самом длинном. Решение — требовать
  цифру в первом сегменте значения на уровне грамматики паттерна, не пост-фильтром.
- `re.IGNORECASE` на весь паттерн контекстного детектора незаметно убирал регистрочувствительность
  и у *значения* тоже — из-за этого "account number: 87425693 **wi**ll be charged" ловило
  "wi" как часть значения. Исправлено через `(?i:...)`, ограниченный только ключевой фразой
  (Python 3.11+).

### 2.2 Псевдонимизация (`aliaser.py`)

Двухпроходная схема — согласованность гарантируется по построению:

1. **Инвентарь**: спаны группируются в сущности по (лейбл, нормализованный текст). Для
   персональных лейблов (`first_name`/`last_name`/`user_name`) дополнительно склеиваются
   сущности, чей текст — подстрока другой (разные написания одного имени). На этом датасете
   основной механизм — точное совпадение (имя почти всегда повторяется буква-в-букву).
2. **Псевдоним**: `HMAC(соль_документа, "лейбл:нормализованная_сущность")` → детерминированный
   индекс в пул того же типа (~10-30 значений на категорию: имена, компании, города, категории
   демографии) либо в format-preserving трансформацию для ID/номеров/дат. Один документ + одна
   сущность → всегда один и тот же псевдоним; разные документы (разная соль) → разные псевдонимы.
   При случайном совпадении псевдонима с оригиналом (проверено на данных — редко, но
   происходит) — детерминированный retry с "подсоленным" ключом.
3. **Format-preserving подстановка**: телефон/ID остаются тем же классом символов
   (цифра→цифра, буква→буква с сохранением регистра, разделители не трогаем); номер карты —
   с валидным контрольным разрядом Луна (наш псевдоним честнее исходных данных); дата/дата
   рождения/datetime сдвигаются на **одну и ту же случайную константу для всего документа**
   (сохраняется относительная хронология, не только формат); email — локальная часть
   заменяется на псевдо-имя, публичные почтовые провайдеры (gmail/hotmail/...) не трогаются,
   кастомные корпоративные домены заменяются на псевдо-компанию.
4. **Замыкание повторов**: если сущность уже опознана, но её точный текст встречается в
   документе ещё раз без подписи поля рядом (контекстный детектор второе вхождение не поймал
   бы сам по себе) — подстановка всё равно заменяет все вхождения. Это отдельный под-проход,
   добавленный после того, как self-audit на реальных данных нашёл именно такие утечки
   (см. раздел 3). Короткие/generic значения (pin, cvv, age, time) из этого прохода исключены —
   риск случайно заменить постороннее число перевешивает пользу.
5. **Vault**: список `{label, alias, original_values, occurrences}` на документ — легитимная
   деанонимизация возможна при наличии vault и права на его просмотр.

## 3. Self-audit (leak rate)

`verify.py` прогоняет анонимизированный текст детекторами повторно и сверяет находки с
множеством исходных значений. **Важный методологический момент**, найденный на реальных
данных: наивная проверка "детектор снова что-то нашёл → утечка" даёт ложную тревогу, потому
что подстановка **format-preserving** — псевдо-номер карты снова выглядит как номер карты, это
и есть цель, не баг. Поэтому считаются раздельно:

- **`true_leak_rate`** — доля повторно найденных спанов, чей текст совпадает с ОРИГИНАЛЬНЫМ
  значением (детектор нашёл ту же реальную сущность — подстановка её не задела). Целевое — 0.
- **`literal_leak_rate`** — независимая от детектора проверка: оригинальный текст спана ищется
  подстрокой в анонимизированном документе (значения короче 4 символов не считаются — слишком
  шумно, 2-3-значная подстрока почти всегда совпадает случайно с фрагментом другого числа).
- **`residual_pii_shaped_rate`** — ожидаемо большая доля (это НЕ утечка, а следствие
  format-preserving дизайна): после анонимизации текст всё ещё выглядит как PII, потому что
  выглядеть правдоподобно — и есть требование задания.

**Результат на 2000 документов (8051 span):**

| метрика | значение |
|---|---|
| `true_leak_rate` | **0.0000** (0 из 8051) |
| `literal_leak_rate` | 0.0002 (2 из 8051) |
| `doc_leak_rate` (доля документов хоть с одной утечкой) | 0.001 (2 из 2000) |
| `residual_pii_shaped_rate` (ожидаемо, не утечка) | 0.893 |
| согласованность (один текст → всегда один псевдоним в документе) | 100% (0 нарушений на 2000 документов) |

Два оставшихся `literal_leak_rate`-случая — оба на лейблах `pin`/`time`, намеренно исключённых
из "замыкания повторов" (пункт 4 выше) из-за риска ложной замены постороннего числа; это
задокументированный компромисс, не забытый баг. Три реальных бага, найденных именно этим
self-audit циклом и исправленных до текущего состояния: (1) ISO-datetime с суффиксом `Z` не
парсился и оставался в тексте as-is; (2) `ipv6`-паттерн перехватывал обычное время `HH:MM:SS`
(2 двоеточия — недостаточно строгий критерий); (3) редкая (~0.1% на сущность) случайная
коллизия HMAC-псевдонима с оригиналом на коротких значениях — закрыта детерминированным retry.

### Где детекторы реально слабы (среди покрываемых типов)

- **`ipv6` (precision 0.267)** — главный оставшийся источник шума: свободные буквенно-цифровые
  строки с двоеточиями (не только время — исправлено, но и другие colon-separated форматы)
  иногда всё ещё матчатся. Требует более строгой валидации (полная RFC-грамматика IPv6 вместо
  эвристики) — не сделано из-за низкого объёма типа в датасете (48 из 17 168 gold-спанов).
- **`credit_debit_card` (precision 0.476)** — без проверки Луна (она здесь не работает, см.
  раздел 1) детектор ловит любой 13-19-значный цифровой пробег с разделителями; часть false
  positive — это на самом деле `account_number`/`customer_id`, у которых случайно длинное
  значение. Граница между "номер карты без подписи" и "просто длинный ID" в этом датасете
  местами объективно неразличима без контекста.
- **`api_key`/`unique_id`/`device_identifier` (recall 0.32-0.43)** — компромисс в пользу
  precision: узкий разрыв между подписью поля и значением (см. `ASSIGNMENT_GAP` в
  `detectors.py`) специально сужен после того, как self-audit нашёл ложные срабатывания
  `password`-детектора на обычных английских словах ("...the password **should** be strong...").
  Та же строгость снижает recall на соседних ID-подобных типах. Осознанный выбор: лучше
  не поймать часть API-ключей, чем анонимизировать случайное предложение как секрет.
- **`postcode` (recall 0.434)**, **`time` (recall 0.499)** — широкий разброс форматов
  (US 5-значный / UK буквенно-цифровой; 12- и 24-часовое время) не покрыт одним паттерном
  полностью.

Эти пробелы — честная картина возможностей чистого regex-слоя, не результат недоделанной
работы над конкретными паттернами: каждый описанный компромисс — задокументированное решение
в пользу precision там, где альтернатива повышала бы recall ценой ложных срабатываний,
проверенных на реальных данных self-audit циклом.

## 5. Где нужен LLM-слой

20 из 55 типов (**ровно половина PII-упоминаний в датасете**) принципиально не имеют формата:
`first_name`, `last_name`, `user_name`, `company_name`, `occupation`, `city`, `state`, `county`,
`country`, `street_address`, `race_ethnicity`, `religious_belief`, `political_view`,
`sexuality`, `blood_type`, `language`, `gender`, `education_level`, `employment_status`, `age`.

Промпт для этого прохода — `cases/pii/prompts/context_entities.md`. Контракт: вход — сырой
текст + `document_type`/`domain` для калибровки, выход — **только JSON**-список спанов в том
же формате `{start,end,label,text}`, лейбл — из фиксированного списка (не свободный текст),
каждый спан валидируется сверкой `text == doc[start:end]` до использования (несовпадающие
оффсеты отбрасываются, не "верятся на слово" — они бесполезны для format-preserving
подстановки в `aliaser.py`, которая уже работает с любым источником спанов одинаково).
**Не вызывался** — ключей LLM в окружении нет, живые вызовы запрещены по условиям задания.

## 6. Согласованность и vault — проверено, не только заявлено

- **Одна сущность = одна замена во всём документе**: инвентарь строится ДО подстановки
  (двухпроходность), поэтому это гарантия архитектуры, а не удача. Проверено прогоном: 0
  нарушений согласованности на 2000 документов (одинаковый нормализованный текст сущности
  внутри документа всегда получает один и тот же псевдоним).
- **Vault**: `aliaser.anonymize()` возвращает список `{label, alias, original_values,
  occurrences}` — обратное отображение для легитимной деанонимизации. В демо-прогоне
  (`out/pii/case1_pii_sample.json`) vault сохранён для каждого документа.
- **Соль**: `HMAC(secret + doc_id, "лейбл:значение")` — псевдонимы одной и той же сущности
  различаются между документами (нет сквозной деанонимизации по псевдониму между документами),
  но воспроизводимы при повторном прогоне того же документа с тем же секретом. Секрет — константа
  демо-уровня в `aliaser.py`, в проде должен приходить из KMS/секрет-стора (явно отмечено в коде).

## 7. Ablation (что дало детекторный слой без LLM)

Полный гибрид (detectors + LLM-слой из раздела 5) не прогонялся — нет ключей. Единственная
измеримая конфигурация — **только детекторы**, её честные цифры — весь раздел 4. По построению
архитектуры (двухпроходный aliaser, работающий с любым источником спанов одинаково) ablation
"detectors / LLM / гибрид" сводится к тому, чей список спанов подаётся на вход `anonymize()` —
никакого отдельного кода для гибридного режима не требуется, добавление реального LLM-вызова
не меняет `aliaser.py`/`verify.py`.

## 8. Файлы

- `cases/pii/detectors.py` — детерминированные детекторы (STANDALONE + CONTEXT + даты).

- `cases/pii/verify.py` — self-audit (true/literal/residual leak rate).
- `cases/pii/evaluate.py` — span-level precision/recall/F1 против эталона, per-type таблица.
- `cases/pii/__init__.py` — `PLUGIN` для `core.pipeline` / `run.py --case 1`.
- `cases/pii/prompts/context_entities.md` — промпт LLM-слоя (не вызывался).
- `out/pii/detectors_metrics.json` — полные метрики прогона (`--n 2000`).
- `out/pii/self_audit_summary.json` — агрегированный self-audit (`--n 2000`).
- `out/pii/case1_pii_sample.xlsx`, `out/pii/case1_pii_sample.json` — выгрузка 500 документов:
  `doc_id`, найденные PII-лейблы, число заменённых сущностей, `true_leak_rate`,
  анонимизированный текст (полный `Verdict` с vault — в json).
