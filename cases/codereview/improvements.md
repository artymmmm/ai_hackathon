# Кейс 3 — попытки превзойти каскад cert_only + ступень2(uncertain), F1=0.575

Эталон: `out/bench/case3_eval_ids.txt` (150 id, 50 vulnerable / 100 secure). Все числа —
из `cases/codereview/out/eval_metrics_*.json` (посчитаны `evaluate.py`), сведены в
`cases/codereview/out/configs_comparison.csv` (23 строки). Действующий лучший результат —
**каскад cert_only+ступень2(uncertain) k>=3/5: F1=0.5747, FPR=0.12** (`case3_deepseek-chat_cascade_B_k3of5.json`).
Ни одна из проверенных здесь конфигураций его не превзошла при FPR<=0.12.

## Итог по трём целям

### Цель 1 — офлайн-комбинация screener (SENSITIVE) + cert_only

Без единого вызова LLM (`cases/codereview/combo_analysis.py`):

- `union` (vulnerable у любого из двух): F1=**0.494**, FPR=**0.17** — recall подрос до 0.44,
  но FPR вышел за 0.12 (у screener и cert_only False Positive попадают на разные фрагменты,
  поэтому их объединение почти удваивает FP). Хуже cert_only одного (F1=0.512, FPR=0.11).
- `intersection` (vulnerable только если оба согласны): F1=**0.378**, FPR=**0.10** — FPR ниже
  порога, но recall упал до 0.28: у детекторов слишком разные срабатывания, пересечение
  почти ничего не ловит устойчиво.
- **Запас в принципе есть, но маленький**: из 50 истинных vulnerable хотя бы один детектор
  ловит 22, cert_only один ловит 21 (recall 0.42×50) — прибавка от объединения всего **+1 из 50**.
  28 из 50 истинных vulnerable не ловит НИ ОДИН из двух детекторов вообще — потолок для любой
  комбинации этих двух конкретных прогонов около recall 0.44, выше не прыгнуть без нового сигнала.
  `cases/codereview/out/combo_stats.json`.
- Каскад на объединённой корзине uncertain (screener 84 ∪ cert_only 89 = 99 id, из них 10 новых
  для LLM, остальные 89 переиспользованы из готовой ступени 2): лучший порог k>=3/5 дал
  F1=**0.475**, FPR=**0.11** — хуже одиночного каскада cert_only (0.575/0.12). Добавление
  screener-эксклюзивных 10 id в корзину эскалации размывает голосование, а не усиливает его.

**Вывод цели 1**: гипотеза "скринер и cert_only ловят разное, комбинация даст прирост" —
частично подтвердилась (запас в 1 фрагмент recall есть), но выигрыш меньше шума и ни один
из четырёх способов комбинирования (union/intersection/cascade-union) не бьёт F1=0.575 при
FPR<=0.12. Гипотеза мертва на числе **+1/50** (запас) против **-0.08…-0.10 F1** (реальная цена
комбинирования из-за роста FPR или потери recall).

### Цель 2 — расширение ступени 2 на secure-корзину cert_only

Новые вызовы: 29 secure-id × 5 сэмплов = 145 вызовов, `run_extended_stage2.py`.
Проверка на схлопывание сэмплов: среднее число уникальных ответов на фрагмент = **5.00/5**
у всех 36 новых id (0 фрагментов с идентичными 5/5) — голосование не бессмысленно технически,
модель реально сэмплирует по-разному (`cases/codereview/out/extended_stage2_diversity_check.json`).

Но по содержанию голосов: из 29 secure-фрагментов cert_only **28 получили 0 голосов "vulnerable"
из 5** на форсированном бинарном промпте, и только 1 (id 110340, единственный с confidence=0.8,
тоже входящий в "low confidence") получил 1 голос из 5.
`cert_only+ступень2(uncertain∪secure_all)` и `cert_only+ступень2(uncertain∪secure_lowconf)`
поэтому дают **идентичные метрики** на каждом пороге k (единственная разница — тот же id 110340):

| порог | P | R | F1 | FPR | эскалация к людям | вызовов LLM |
|---|---|---|---|---|---|---|
| k>=1/5 | 0.509 | 0.56 | 0.533 | 0.27 | 55/150 (36.7%) | 740 (secure_all) / 605 (lowconf) |
| k>=2/5 | 0.587 | 0.54 | 0.562 | 0.19 | 46/150 (30.7%) | 740 / 605 |
| k>=3/5 | 0.676 | 0.50 | 0.575 | 0.12 | 37/150 (24.7%) | 740 / 605 |
| k>=4/5 | 0.667 | 0.44 | 0.530 | 0.11 | 33/150 (22.0%) | 740 / 605 |

При k=1 расширение стоит **1 дополнительный ложный флаг** (fp 26→27) и F1 чуть ниже, чем у
базового каскада cert_only (0.5385→0.5333); при k>=2 результат бит-в-бит совпадает с
`cascade_B_k{k}of5` — то есть все 145 (или 10, для low-conf-варианта) дополнительных вызовов
LLM на secure-корзине не изменили НИ ОДНОГО финального вердикта.

**Вывод цели 2**: гипотеза "модель неуверенно говорит secure и там прячется recall" —
**умерла на числе 28/29 = 0.966** (доля secure-фрагментов, где форсированный бинарный
повторный проход единогласно (5/5 или 4/5) подтвердил "secure"). Ставка на низкую confidence
как признак ошибки тоже не работает: confidence в этой корзине квантована в {0.8, 0.9, 0.95}
(см. закрытый тупик "порог по confidence" в предыдущих экспериментах), и единственный id с
самой низкой confidence (0.8) — тот самый, что дал слабый 1-голосный флип. Расширение области
применения ступени 2 покупает FPR (при k=1) или платит вызовами без эффекта (при k>=2), recall
не растёт.

### Цель 3 — сводная таблица

`cases/codereview/out/configs_comparison.csv`, 23 строки, колонки: конфигурация, P, R, F1, FPR,
эскалация, tp, fp, fn, tn, число_вызовов_LLM, к_человеку_n, к_человеку_доля_корпуса,
уязвимых_доходит_до_человека, чистого_кода_в_очереди, файл_вердиктов.

Операционное чтение (эскалация в `evaluate.py` занижена: uncertain считается как secure, реальный
человеческий поток = vulnerable+uncertain):

- Все конфигурации без форсированной ступени 2 (голая LLM, скринер, config A, cwe_only,
  cert_only) отправляют человеку **32-81% корпуса** — cert_only при formal F1=0.512 фактически
  выгружает 121/150 (80.7%) фрагментов в очередь, из них 77% — чистый код. Это НЕ экономия,
  несмотря на приличный F1: `evaluate.py` засчитывает uncertain как "пропущено", но операционно
  это "человек посмотрит почти весь корпус".
- Каскад cert_only+ступень2 (любой k) убирает эскалацию до 0 (форсированный бинарный проход не
  оставляет uncertain) — человеку уходит только предсказанный vulnerable: 22-36% корпуса в
  зависимости от порога, k>=3/5 — 37/150 (24.7%), из них реально уязвимых — 25/50 (50% recall),
  чистого кода среди них — 12/100 (12%). Это первая конфигурация, где "к человеку" и "F1" не
  противоречат друг другу.
- Все варианты цели 1 и 2 не улучшают эту картину: combo-конфигурации либо дороже по вызовам
  LLM (300-795 против 150-595) и не лучше по F1/FPR, либо (secure_all/secure_lowconf) стоят
  дополнительных вызовов при нулевом эффекте на итоговый вердикт.

## Что улучшало метрику (числа)

- cert_only vs config A: **+0.170 F1** (0.512 vs 0.342) — целевой CERT-блок сильно лучше общего
  CWE+CERT+flawfinder стека (ранее задокументировано, не переизмерялось здесь).
- Форсированная ступень 2 (бинарный промпт, запрет uncertain, "перевёрнутая рамка") на
  cert_only-uncertain, k>=3/5: **+0.063 F1** (0.512→0.575) и эскалация 0.593→0.0 — единственная
  конфигурация, которая одновременно поднимает F1 и убирает ручную очередь как категорию.

## Что НЕ улучшало метрику (числа)

- Union screener+cert_only: F1 0.494 (хуже cert_only на -0.018), FPR 0.17 (хуже порога 0.12 на
  +0.05) — recall подрос (+0.02), но ценой FPR.
- Intersection screener+cert_only: F1 0.378 (хуже на -0.134), recall упал до 0.28.
- Каскад по объединённой uncertain-корзине screener+cert_only, k>=3/5: F1 0.475 (хуже
  одиночного cert_only-каскада на -0.100).
- Расширение ступени 2 на всю secure-корзину cert_only (29 id, 145 вызовов): F1 не меняется
  на k>=2/5 (бит-в-бит совпадает с базовым каскадом), при k=1/5 даже хуже (-0.005 F1, +1 FP).
  145 вызовов LLM полностью потрачены впустую на этой выборке.
- Расширение только на low-confidence secure (2 id, 10 вызовов): идентично предыдущему пункту
  — единственный "интересный" id (110340) входит в обе группы.
- (Ранее закрытые тупики, не переизмерялись здесь, только упоминаются: критик поверх ступени 1
  F1=0.265; состязательный суд прокурор/защита/судья F1=0.076; порог по полю confidence —
  бесполезен из-за квантования; корпусные методы logreg/retrieval — F1=0.000 кросс-проектно.)

## Прямой ответ

**F1=0.575 при FPR<=0.12 не превзойдено.** Лучший результат остаётся каскад
cert_only+ступень2(uncertain) k>=3/5, F1=0.5747, FPR=0.12 (`case3_deepseek-chat_cascade_B_k3of5.json`).
Ближайший конкурент — те же метрики бит-в-бит у `stage2_secure_all_k3of5` /
`stage2_secure_lowconf_k3of5`, но они строго хуже по стоимости (740/605 вызовов против 595) при
равном качестве, то есть не считаются улучшением.

Обе проверенные здесь гипотезы прироста recall не подтвердились числом:
1. "screener ловит то, что не ловит cert_only" — запас всего +1 истинный vulnerable из 50
   (recall потолок 0.44 против 0.42 у одного cert_only), а цена комбинирования (рост FPR или
   падение recall) больше этого запаса.
2. "в secure-корзине cert_only прячутся неуверенные ложные secure" — 28 из 29 secure-фрагментов
   единогласно (0-1 голос из 5) подтвердились форсированным повторным проходом; расширение
   ступени 2 туда не меняет ни одного финального вердикта на порогах k>=2/5.
