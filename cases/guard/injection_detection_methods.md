# Методы детекции prompt injection помимо TF-IDF+LogReg / LLM-судьи

Разведка для кейса 2 после диагностики потолка (F1=0.9844 офлайн / 0.989 гибрид, все 99 FN —
класс 1, замаскированные инъекции; см. `cases/guard/case2_notes.md`). Каждое число — со
ссылкой; где источник не даёт число — сказано прямо.

## 1. Специализированные классификаторы-энкодеры

**ProtectAI deberta-v3-base-prompt-injection** (DeBERTa-v3-base, 0.2B параметров, Apache 2.0).
Обучен на HuggingFaceH4/ultrachat_200k + rubend18/ChatGPT-Jailbreak-Prompts + fka/prompts.chat +
собственный набор (~30% инъекций / 70% нормальных). На своём eval-сплите: accuracy 0.9999,
precision 0.9998, recall 0.9997, F1 0.9998.
Источник: model card, https://huggingface.co/protectai/deberta-v3-base-prompt-injection.
v2-версия по вторичному источнику (не проверено напрямую) заявляет 99.93% на своём eval и
95.25% «на нетренированных датасетах» — https://dataloop.ai/library/model/protectai_deberta-v3-base-prompt-injection-v2/.

**Meta Llama Prompt-Guard-86M** (mDeBERTa-v3-base, 86M backbone + 192M embeddings = 0.3B итого,
лицензия Llama 3.1 Community). TPR/FPR/AUC по срезам eval-сета:

| срез | TPR | FPR | AUC |
|---|---|---|---|
| Jailbreaks | 99.9% | 0.4% | 0.997 |
| Injections | 99.5% | 0.8% | 1.000 |
| OOD Jailbreak | 97.5% | 3.9% | 0.975 |
| Multilingual Jailbreak | 91.5% | 5.3% | 0.959 |
| CyberSecEval Indirect Injections | 71.4% | 1.0% | 0.966 |

Источник: model card, https://huggingface.co/meta-llama/Prompt-Guard-86M. Модель прямо
предупреждает: «not immune to adaptive attacks» (открытые веса — атакующий может их изучить), и
OOD/мультиязычные метрики заметно хуже in-distribution. Есть более новая Llama Prompt Guard 2
(86M и облегчённая 22M на DeBERTa-xsmall) — конкретных цифр её eval не проверял.

**Вес и требования (не качать без отдельного разрешения — так и осталось не скачано):**
DeBERTa-v3-base ≈ 0.2B параметров ≈ 700 МБ fp32 / ~350 МБ fp16 на диске, инференс на CPU
единицы-десятки мс/документ; Prompt-Guard-86M чуть тяжелее (0.3B). Оба явно тяжелее
model_a.joblib (≈3 МБ, TF-IDF+LogReg, инференс на CPU — доли мс/документ).

## 2. Бенчмарк PINT (Lakera) и его проблема ровно того же рода, что мы уже видели в кейсе 3

PINT: 4314 входов (3016 EN + 1298 не-EN), инъекции — только 5.2% выборки (сильный дисбаланс в
пользу benign/других категорий). Заявлено, что ни одно из оцениваемых решений не обучалось
напрямую на PINT — независимость от полигона декларируется.
Источник: https://github.com/lakeraai/pint-benchmark (DETAILS.md), https://www.lakera.ai/blog/lakera-pint-benchmark.

Leaderboard (снят 2025-05-02..2025-08-27):

| решение | PINT accuracy |
|---|---|
| Lakera Guard | 95.22% |
| AWS Bedrock Guardrails | 89.24% |
| Azure AI Prompt Shield | 89.12% |
| protectai/deberta-v3-base-prompt-injection-v2 | **79.14%** |
| Llama Prompt Guard 2 (86M) | 78.76% |
| Google Model Armor | 70.07% |
| Aporia Guardrails | 66.44% |
| Llama Prompt Guard (v1) | **61.82%** |

**Это и есть признанная проблема бенчмарков, по аналогии с тем, что мы уже знаем про утечки/
переобучение в кейсе 3 (корпусные методы обваливаются кросс-проектно):** ProtectAI заявляет
accuracy 0.9999 на своём eval, но независимый бенчмарк даёт 79.14% — падение на ~21 п.п. для
той же модели. Llama Prompt Guard v1 заявляет TPR 99.5-99.9%/AUC до 1.000 на своём eval, но на
PINT — 61.82%, падение почти на 38 п.п. Даже создатель бенчмарка (Lakera) на собственном
решении получает не 100%, а 95.22% — детекция prompt injection остаётся открытой задачей, а не
вопросом «докрутить датасет». Оговорка в самом PINT: решения были «optimally configured» —
лучший случай, не обязательно то, что будет в реальном деплое.

## 3. Приёмы против обфускации

- **Unicode NFKC-нормализация** сворачивает совместимые гомоглифы (кириллическая «і» → латинская
  «i») к канонической форме до токенизации; рекомендуется как минимальный defense-слой перед
  любой векторизацией — стрип zero-width, bidi-override, символов из блока Tags.
  Ограничение: NFKC не ловит все confusables (например, «Negative Squared Latin Capital Letters»
  не сворачиваются, т.к. формально не эквивалентны по NFKC) — для полного покрытия нужен
  Unicode TR39 (skeleton/confusables matching).
  Источник (практический блог-пост, не стандарт сам по себе):
  https://dev.to/dokasuka_don_de7635cc481c/is-that-really-a-how-homoglyph-attacks-bypass-llm-security-filters-with-python-examples-17ni.
- **Декодирование base64/hex/rot13/leetspeak и разбиение слов вставленными символами** —
  описано в практических (не рецензируемых) обзорах техник обхода как распространённый паттерн
  атак («token smuggling»); конкретных цифр эффективности контрмеры не нашёл, только описание
  приёма. Источники: https://dev.to/joergmichno/12-ways-attackers-bypass-prompt-injection-scanners-we-built-defenses-for-all-of-them-506k,
  https://medium.com/@instatunnel/token-smuggling-bypassing-filters-with-non-standard-encodings-dceb3d8472a8.
- **Прямой замер на нашем evasion-паттерне (наши же 99 FN):** ни homoglyph, ни base64/hex не
  встречены ни разу — обфускация в датасете кейса 2 другая: посимвольная перестановка соседних
  букв внутри слов («typo-cipher», ~9-10 из 99 FN) и emoji-последовательности (6 из 99).
  NFKC/TR39 эти два паттерна не ловят вообще (это не про гомоглифы), decode-слой тоже мимо (это
  не base64/hex/rot13) — литературные контрмеры этого раздела не целятся в наш конкретный тип
  обфускации.

## 4. Признаки структуры вместо лексики

Раздел частично из литературы, частично — прямое наблюдение по `case2_errors_full_test.csv`
(размечено явно, где что).

- **Perplexity-based (Alon & Kamfonas, arXiv:2308.14132, "Detecting Language Model Attacks with
  Perplexity")**: перплексия по GPT-2 как сигнал аномальности; ~90% адверсариальных запросов
  (GCG-суффиксного типа) дают perplexity выше 1000, LightGBM на (perplexity, длина токенов)
  «resolved false positives and correctly detected most adversarial attacks» в их тесте.
  **Важная оговорка, не из статьи, а из нашего датасета:** метод целится в GCG-style атаки —
  оптимизированные бессмысленные суффиксы, которые ломают перплексию именно потому что не
  похожи на естественный язык. Наши 99 FN — почти все связная беглая английская проза
  («in the realm of...», «just like when...») с низкой, а не высокой перплексией; этот метод
  прицельно не по нашей проблеме, ожидать эффекта от него на нашем FN-наборе не стоит.
- **Не-ASCII доля, энтропия, доля кода, длина** — уже реализованы в `cases/guard/features.py`
  (`non_ascii_ratio`, `shannon_entropy`, `special_char_ratio`, `has_code_block`,
  `curly_brace_ratio`, `hex_run_count`, `zero_width_count`) и используются в model_b. Но
  model_b **на полном тесте уже хуже** model_a: F1=0.9654 против 0.9844 (`out/guard/metrics.json`,
  числа уже посчитаны, не из статьи) — сами по себе эти признаки без word/char TF-IDF слабее
  лексической модели, не сильнее.
- **Императив/смена языка внутри документа** — конкретных бенчмарков не нашёл; прямое
  наблюдение по нашим 99 FN: 36% содержат явный код-подобный синтаксис (скобки/`fn`/`func`/
  `let mut`/`=>`), медиана длины — 40 слов (не короткие обрывки), почти нет прямых триггерных
  фраз в начале предложения — команда почти всегда встроена в середину/конец декоративного
  абзаца. Смена языка внутри документа встречена 1 раз из 99 (см. `case2_notes.md`, пример
  `case2-test-6845`, испанский триггер внутри немецкого вопроса).

## 5. Embedding-based без дообучения

Найдена одна свежая работа с подходящим названием — «Zero-Shot Embedding Drift Detection»,
arXiv:2601.12359 — не читал полностью (не хватило времени в рамках разведки), числ не извлекал,
поэтому не привожу цифр. По общей идее zero-shot embedding подходов (ближайший сосед / дрейф
эмбеддинга от кластера «нормальных» промптов) в найденных источниках прямых чисел для наших
условий (короткие банковские запросы, английский, 3-класcная задача) не нашёл — эффективность
без замера на наших данных не утверждаю.

## 6. Итог разведки — стоит ли овчинка выделки

- Специализированные encoder-классификаторы (DeBERTa-семейство) заявляют near-100% на своих
  eval-сетах, но теряют 20-38 п.п. на независимом бенчмарке (PINT) — тот же паттерн
  cross-project коллапса, что мы уже видели в кейсе 3. Скачивать/использовать без замера на
  НАШИХ данных смысла нет — цифры производителя ничего не говорят про наш домен (банковский
  ассистент, английский, короткие тексты). Не скачивал и не запускал (по прямому запрету).
- Обфускация в литературе (гомоглифы, base64, GCG-суффиксы) — не тот тип обфускации, что в
  99 FN нашего датасета (typo-cipher внутри слов + emoji + беглая camouflage-проза). Готовые
  контрмеры из разведки прицельно мимо; проверять их на наших данных — трата бюджета.
  Единственное, что бьёт точно в цель по нашим данным — собственные наблюдения (раздел 4):
  code-like синтаксис (36% FN) и посимвольная обфускация (~10% FN) — это и есть кандидаты
  для офлайн-экспериментов (см. `out/guard/` метрики вариантов).
